# 11 — A runtime mode change does not reach a live agent

**What to build:** a decision, and then whatever it implies — a runtime mode the
developer changes mid-conversation currently does not reach the `claude` process
already serving it, so the agent goes on working under the mode the conversation
started with.

Found while building ticket 02, which is why it is numbered after the spec's ten
rather than inside them. It is **not** a regression that ticket introduced: the
per-turn override on `thread.turn.start` has had the same hole since the turn
machinery landed, and ticket 02 only made it reachable from a second control.

## What happens

One child serves a whole conversation — `socket_turn.rs`'s
`one_subprocess_serves_the_conversation_and_is_reaped_when_the_server_stops` is
the test that says so — and `--permission-mode` is passed once, when the process
is opened (`crate::turn::open`, via `crate::agent::permission_mode_for`). The
agent protocol has no control request that moves it afterwards; nothing in
`fixtures/claude-cli/` or the STEP 1 spike shows one.

So a developer who tightens `full-access` to `approval-required` sees the picker
move, sees it survive a restart, and sees the next turn _requested_ under the new
mode — and the agent keeps bypassing permissions until its process is replaced,
which today only happens at a restart or after a session error.

There is a second face of the same thing. The driver publishes
`session.runtimeMode` from the `Start` it captured at the **first** turn
(`crate::turn`, four sites off `start.runtime_mode`), while
`Shell::start_turn` publishes the `starting` session from the _thread_. So one
turn can announce two different modes: the new one as it starts and the old one
as it enters `running`. The UI renders that field beside the session state, so
the badge flips and flips back.

## The decision this needs first

Whether a runtime mode change should **replace the session**. It is not free:

- Killing and re-`--resume`ing costs a fresh `init`, and the CLI's warm context
  window with it.
- `approval-required` is expressed by passing _no_ flag and answering the
  permission callback, so the two directions are not symmetrical — loosening and
  tightening do not cost the same thing.
- Snooze's rule in the spec is "governs attention, never the agent". A mode is
  the opposite: it is entirely about the agent, so there is no precedent here to
  borrow.

The cheap alternative is to leave the process alone and stop claiming otherwise:
publish `session.runtimeMode` from the thread rather than from the captured
`Start`, so at least the two events for one turn agree, and say in the UI that a
mode takes effect for the next session. That is a smaller change and a worse
answer, and which of the two is wanted is a human call.

recorded in the comments below, along with the evidence that settled it.

**Status:** done

## Comments

> *This was generated by AI during triage.*

### Triage: the premise was wrong, and the decision is cheaper than either option

This ticket asked for a human call between replacing the session and giving up on
the claim. Neither is needed. **The agent protocol does have a control request
that moves a running child's mode** — this ticket's "nothing in
`fixtures/claude-cli/` or the STEP 1 spike shows one" was true of the fixtures and
false of the protocol.

Probed against the installed CLI (2.1.220) with this server's exact launch flags,
including `--permission-prompt-tool` and an opening `--permission-mode
bypassPermissions`:

```
→ {"type":"control_request","request_id":"probe-tighten",
   "request":{"subtype":"set_permission_mode","mode":"default"}}
← {"subtype":"success","request_id":"probe-tighten","response":{"mode":"default"}}
← {"type":"system","subtype":"status","permissionMode":"default",...}

→ ... "mode":"bypassPermissions"
← {"subtype":"success","request_id":"probe-loosen","response":{"mode":"bypassPermissions"}}

→ ... "mode":"not-a-mode"
← {"subtype":"error","error":"Cannot set permission mode: must be one of
   acceptEdits, auto, bypassPermissions, default, dontAsk, plan"}
```

Three things fall out. The kill-and-`--resume` cost the ticket weighed — a fresh
`init`, the warm context window — **is not a cost that has to be paid**. The
asymmetry it worried about **dissolves**: `approval-required` maps to no *launch
flag*, but it maps cleanly to the CLI's `default` as a pushed mode, so loosening
and tightening are the same operation in opposite directions. And the CLI
**confirms** the change twice — a `control_response` naming the mode it moved to,
and a `system`/`status` line carrying `permissionMode`.

### What upstream does, since ADR-0012 makes it the specification

Upstream's `ClaudeAdapter` holds a live query handle and calls
`setPermissionMode` on it — the SDK's wrapper for this same control request — **at
turn dispatch**, beside a `setModel` guarded on the model having actually changed.
So upstream independently confirms both the mechanism and the moment.

But it pushes only for **interaction** mode: `plan` becomes the CLI's `plan`, and
`default` restores a `basePermissionMode` captured once at session start from the
runtime mode. Nothing in its turn path reads `runtimeMode` again. **Upstream has
this same defect**, which is why the parity ledger did not catch it — laplus is at
parity here rather than behind. Upstream's is in one respect worse: because
`basePermissionMode` is a captured constant, leaving plan mode after a
runtime-mode change restores the mode the conversation opened with. This server
cannot inherit that, because it never sends interaction mode to the CLI at all.

Two things to take from upstream rather than re-derive: `?? "default"` for the
no-flag case is **its** convention, so mapping `approval-required` to `default` is
following upstream; and the push is guarded on the mode having changed.

## Agent Brief

**Category:** bug
**Summary:** Neither a runtime mode change nor a model change reaches the
`claude` already serving the conversation. Push both on the agent's control
channel at the next turn, rather than replacing the session or weakening the
claim.

**Current behavior:**
A session captures everything it needs once, when it opens, and the driver task
holds that capture for the life of the conversation. `--permission-mode` is
translated from the thread's runtime mode and given to the child at launch,
`--model` is given from the thread's model selection at the same moment, and the
driver's copy of the runtime mode is what every session event it publishes
reports. Later turns are pushed down a channel to a driver that is already
running, so none of these values move.

A developer who tightens `full-access` to `approval-required` therefore sees the
picker move, sees it survive a restart, sees the next turn *requested* under the
new mode — and the agent goes on bypassing permissions until its process is
replaced, which today happens only at a restart or after a session error.

**The model has the identical defect and is the same fix, so it is in scope
here.** A model selection is a property of the thread, editable mid-conversation
by `thread.meta.update`, read into the session's capture once, and used in
exactly one place — the launch flag. So a developer who switches model mid-
conversation is answered by the model they started with, having been shown the
one they picked. Splitting this into a second ticket would mean building the same
mechanism twice, since it is the same channel, the same moment, the same
guard-on-change and the same refusal path.

The same capture produces a second, visible symptom: the `starting` session is
published from the thread, and `running` and the settled and error publishes are
published from the driver's captured mode. One turn announces two different modes
and the badge beside the session state flips and flips back.

**Desired behavior:**
When a turn is dispatched under a runtime mode that differs from the one the
child is currently running under, the server tells the child to change, on the
control channel, before the turn is sent — and the child keeps serving the
conversation. No new process, no `--resume`, no re-`init`, no lost context
window.

The moment is the **next turn's dispatch**, not the moment the picker's command
commits. Ticket 02 and the spec's story 29 already fix that a mode set now applies
to the next turn and must not move the rules under a running agent's feet; this
must not change that.

Every session event for one turn reports one mode. After a successful push, the
driver's own copy is the new mode, so `starting`, `running` and whatever ends the
turn agree.

A push the CLI refuses is a failure the developer is told about, and it does not
leave the session claiming a mode it is not running under.

**Key interfaces:**

- `crate::protocol` gains a builder for this control request, beside the ones for
  `interrupt` and `get_context_usage`. Those two are the precedent in shape and in
  provenance — both were found by reading the binary, and this is a third.
- The mode it carries is the **CLI's** vocabulary, not the contract's.
  `crate::agent::permission_mode_for` answers `None` for `approval-required`
  because upstream expresses it by passing no launch flag; a pushed mode has no
  such option and needs a total translation, in which `approval-required` becomes
  `default`. **Leave the launch table lossy** — passing a flag for
  `approval-required` at launch would be a different and wrong change. The two
  translations are separate functions answering separate questions.
- `crate::threads::Signal` is how something reaches a driver ahead of the turns
  queued for it, and is where the mode change belongs, for the same reason
  `Interrupt` and the session stop travel it.
- The driver's captured `Start` carries the `runtime_mode` that every session
  publish reads. It is the thing that must move when a push succeeds — that is
  what closes the second symptom, and it closes it without a separate fix.
- The CLI answers on two lines: a `control_response` for the request id, and a
  `system` line whose subtype is `status` carrying `permissionMode`. The first is
  the one to key the outcome off; the second is currently unrecognised and folds
  to nothing, which is acceptable but worth knowing.
- The model push is a `set_model` control request on the same channel, and takes
  the **bare slug the thread already holds** — `opus` is accepted and resolved by
  the CLI to `claude-opus-5`. It needs none of upstream's api-id resolution, so
  what `Start` carries for the launch flag is what the push carries too. An
  unrecognised model is refused with a sentence, like an unrecognised mode.

**One trap, verified and easy to ship by accident.** A `set_model` push makes the
CLI emit a synthetic `user` line whose content is
`<local-command-stdout>Set model to opus (claude-opus-5)</local-command-stdout>`,
marked `isReplay`. This server's protocol module folds **every** user line into
the transcript, on the stated grounds that it "does not pass
`--replay-user-messages`" and so a user line can only be a tool result. That
reasoning no longer holds — this line arrives without that flag. It most likely
fails to decode and is counted as drift, because its content is a bare string
where a list of blocks is expected, but **confirm which rather than assume**: the
failure this guards against is the developer's transcript growing a turn they did
not type. Whichever way it lands, the module's comment needs correcting, since
its premise is now false.

**Acceptance criteria:**

- [x] After a runtime mode change, the next turn's agent is actually running
      under the new mode — not merely requested under it.
- [x] Tightening works: a conversation opened at `full-access` and moved to
      `approval-required` prompts for permission on the next turn.
- [x] Loosening works: the reverse stops prompting. Both directions are the same
      operation.
- [x] `approval-required` is pushed as the CLI's `default`, rather than as no push
      at all.
- [x] No push is sent when the mode has not changed from what the child is
      already running under.
- [x] A mode set while a turn is running does not move that turn. The push happens
      at the next turn's dispatch. Ticket 02's behaviour is unchanged.
- [x] A push the CLI refuses is reported to the developer in a sentence naming
      what was refused, and the session's published runtime mode continues to
      report what the child is really running under rather than what was asked
      for.
- [x] Every session event for a single turn reports the same runtime mode —
      `starting`, `running`, and the publish that ends the turn.
- [x] The session is not replaced: the agent session id is unchanged across a mode
      change, and the conversation continues rather than restarting.
- [x] The per-turn override on a turn request goes through the same path, since it
      has had this hole for longer than the picker's command has.
- [x] A model changed mid-conversation is what answers the next turn, and the
      session is not replaced to achieve it.
- [x] No `set_model` is sent when the model has not changed.
- [x] A model push does not add a turn to the developer's transcript.
- [x] A capture of the request and its response joins `fixtures/claude-cli/`,
      which is what the absence of one caused this ticket to conclude.
- [x] The line builder is unit-tested in place, as the interrupt and context-usage
      builders are; the socket seam asserts a mode change followed by a turn.
- [ ] Driven in the window, because a green suite is not evidence here — the
      question is what a real child does with a real permission prompt.

**Out of scope:**

- **Replacing the session on a mode change.** This ticket's original framing, and
  the evidence above is why it is not needed.
- **Interaction mode reaching the CLI.** Upstream routes `plan` down this same
  channel; this server stores interaction mode and never sends it. That is
  deliberate and recorded — `CONTEXT.md` says so in both glossaries, and the
  spec's own Out of Scope says publishing a plan needs the plan-exit tool
  answered rather than merely reported, which is its own effort. So it is **not**
  a gap in this mechanism and wants no ticket from this one. If it is ever picked
  up, it must not copy upstream's captured base mode — that is the bug described
  above.
- **Changing `permission_mode_for`'s launch table**, or the closed set of runtime
  modes the contract names.
- **The `system`/`status` line** becoming a folded event in its own right.

### Delivered

`crate::protocol` gained `set_permission_mode_line` and `set_model_line`,
`crate::agent` gained `pushed_permission_mode_for` beside the launch table it
deliberately leaves lossy, `Signal::Retune` carries what a turn wants, and
`crate::turn::retune` spends it at the next turn's dispatch — moving the driver's
`Start` when the write lands and putting it back when the CLI refuses.

Two things beyond the brief, both forced by the trap it named. The replayed
`user` line a `set_model` push produces did **not** merely fail to decode: its
`content` is the Messages API's bare-string shorthand, so the whole line failed
to parse and an ordinary model change was counted as protocol drift. Both halves
are fixed — a bare string is read as one text block, and `isReplay` is read and
the line dropped — and the module comment whose premise had become false is
corrected.

**How it was verified, precisely.** The suite is the usual offline one. Beyond
it, the real `claude` 2.1.220 was driven twice: once directly, to record
`fixtures/claude-cli/20-modes-changed-mid-conversation.ndjson` and
`21-modes-refused.ndjson`, and once *through this server* — a real child, a real
socket, a first turn under `full-access` that wrote a file unasked, a mode
tightened between turns, and a second turn stopped on `Write needs permission`,
with both of that turn's session events reporting `approval-required`. That is
the last criterion's substance, and its box is deliberately left unticked: it was
**not** driven in the browser window. Nothing in this change is client-side and
both things the UI renders — the badge beside the session state and the approval
panel — were asserted on the wire, so the remaining risk is judged small; but the
criterion says the window, and the window is not what was driven.
