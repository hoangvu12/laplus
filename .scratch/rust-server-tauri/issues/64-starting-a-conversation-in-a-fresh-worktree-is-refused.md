# 64 — Starting a conversation in a fresh worktree is refused

> _This was generated by AI during triage._

**What to build:** worktree threads — `vcs.createWorktree`,
`vcs.removeWorktree` and `bootstrap.prepareWorktree`.

**Status:** ready-for-agent

**Found by:** the 2026-07-28 parity audit, ledger M12.

## What happens

The branch toolbar offers to start a conversation in a fresh worktree.
`crate::orchestration` refuses it.

This is the largest single feature in the parity backlog that is not blocked on a
decision — three related methods, all with declared shapes, over a `git` facility
that already works.

## Why it matters beyond the button

Two other findings dead-end here:

- **Project actions** (48) can define `runOnWorktreeCreate`, and nothing runs it.
  That hook has no meaning until worktrees exist.
- Running several agents against the same repository without them fighting over
  the working tree is the thing worktrees are _for_, and laplus already supports
  several conversations at once across projects (ticket 16). Same-project
  concurrency is the gap this closes.

## Key interfaces

- `vcs.createWorktree`, `vcs.removeWorktree` — read their shapes from the
  contract.
- `bootstrap.prepareWorktree` — the thread-creation side. A thread bound to a
  worktree needs its cwd to be the worktree, which touches `crate::agent`'s
  invocation and `crate::git`'s status paths.
- The thread row needs to know which worktree it belongs to, and it must survive a
  restart — a thread whose worktree is gone is a state that will happen.

## What to be careful about

- **Where worktrees are created.** Inside the repository, beside it, or in the
  profile directory are all defensible and they are not equally reversible. Note
  ticket 30 and ADR-0013 exist because laplus once installed on top of its own
  database; putting worktrees somewhere a developer does not expect is the same
  class of mistake.
- **Removal is destructive.** A worktree with uncommitted changes must not be
  removed silently. Decide the rule and make the UI honour it.
- **The file watcher** (ticket 08) and the git status paths (19) both assume a
  project has one working tree. Check what they do with several before assuming
  they cope.
- **Cleanup on thread delete** (49). A deleted worktree thread that leaves its
  worktree behind will accumulate.

## Acceptance

- [ ] Starting a conversation in a fresh worktree creates the worktree and the
      agent runs with it as its cwd.
- [ ] Two conversations on the same project in different worktrees do not see each
      other's edits.
- [ ] Git status, the file tree and the `@`-mention picker all reflect the
      worktree, not the main checkout.
- [ ] Removing a worktree with uncommitted changes follows a written rule rather
      than discarding them silently.
- [ ] A worktree thread survives a restart.
- [ ] A thread whose worktree has been removed outside laplus degrades honestly
      rather than erroring on every request.
- [ ] Deleting a worktree thread does not orphan its worktree — or, if it
      deliberately keeps it, that is stated and visible.

## Out of scope

- `runOnWorktreeCreate` actually executing — that needs 48 first and can follow.
- Any hosted branch or PR integration (spec exclusion).
