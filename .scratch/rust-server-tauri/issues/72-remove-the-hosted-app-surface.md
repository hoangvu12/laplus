# 72 — Remove the hosted-app surface

> _This was generated by AI during a design conversation, 2026-07-29._

**What to remove:** the `app.t3.codes` client path — hosted pairing, hosted-static
mode, and the hosted release-channel selector.

**Status:** done

**Found by:** a conversation about how hosted pairing works, which established
that it cannot work here and would not be wanted if it could.

## What this is

The web bundle can be served from two places: from this server's own binary
(what the desktop window does) or from a CDN at `app.t3.codes`. The second is
"the hosted app". When it runs there it has no backend of its own, so it pairs
with one over the network: `/pair?host=…&label=…#token=…` names a backend,
`POST /oauth/token` trades the token for a bearer, and the browser then talks
directly to that backend. The hosted origin serves HTML and nothing else — it is
not a relay, and no traffic passes through it.

## Why it goes

Three walls, any one of which is fatal, and none of which is an accident:

- **The listener binds to `Ipv4Addr::LOCALHOST`** (`server.rs:321`). Nothing
  off this machine can open a socket to it.
- **`auth::authorize` refuses non-loopback origins** (`auth.rs:132`). A `fetch`
  from `app.t3.codes` is precisely the case that check exists to stop.
- **The endpoints do not exist.** This server routes four HTTP paths
  (`http.rs:1-53`); `/oauth/token` and `/api/auth/pairing-credential` are not
  among them, so neither the mint nor the exchange has anywhere to land. There
  is also no CORS anywhere in the server — the one mention is a comment
  explaining a deliberate omission (`server.rs:508`).

And the reasons upstream has it do not apply. Its three payoffs are a UI that
updates without redeploying a backend, one browser origin holding a catalogue of
many machines, and a console for cloud environments the user does not own.
laplus is one binary that serves its own UI to one machine. `PARITY-LEDGER.md:197`
already files hosted pairing beside cloud and relay.

## What the removal found

**`/pair` is unreachable today, both branches, and it is still not being
removed.** `http.rs:87` hardcodes `authenticated: true`, and says why: answering
`false` "would send the UI to a pairing screen backed by a pairing flow that
does not exist." So `resolveInitialServerAuthGateState` always resolves to
`authenticated` and `pair.tsx:18` redirects to `/`. The local paste-a-code form
is as dead as the hosted one.

It stays anyway. **Ticket 73 builds the server behind it** — a pair code, so a
phone over a tunnel can connect. Deleting the screen and rebuilding it two
tickets later is churn. This ticket removes the _hosted_ half only, and leaves
the local half dead-but-intended.

`isHostedStaticApp()` is likewise always false in this build: no
`VITE_HOSTED_APP_CHANNEL`, and the origin is loopback rather than
`app.t3.codes`. Every `hosted-static` branch is therefore dead too, including an
onboarding empty state nobody has ever seen.

## Comments

Sized during the conversation that produced this ticket. Smaller than ticket 71:
the hosted path is leaf code with one structural tie-in (the gate state union),
where 71 had to reason about a contract divergence and a captured fixture.

### What the removal touched beyond the scope list

Four things the scope list did not name, each a direct consequence of something
it did:

- **`AboutVersionSection` (`SettingsPanels.tsx`) went with the channel select.**
  Its only call site was `{HOSTED_APP_CHANNEL ? <AboutVersionSection/> : <plain
version row>}`, and `git log -L` shows that gate read `isElectron ||
HOSTED_APP_CHANNEL` until `6bd742e` deleted the Electron half. Removing the
  hosted half orphaned the component, so it went by the same reasoning. Settings
  → About renders the plain version row, exactly as it did before this ticket.
  The desktop update surface is untouched and still lives in the sidebar
  (`SidebarUpdatePill`, `Sidebar.tsx`).
- **`HostedStaticEnvironmentBootstrap` (`__root.tsx`) went too.** It activated
  the first saved environment when no `PrimaryConnectionTarget` existed — a state
  only hosted-static could produce. With the gate state gone,
  `primaryEnvironmentAuthenticated` is implied by the guard above it, so the
  three `? … : null` ternaries around `AuthenticatedTracingBootstrap`,
  `EventRouter` and `ProviderUpdateLaunchNotification` collapsed to
  unconditional renders.
- **`endpoint.compatibility.hostedHttpsApp` is no longer read** — neither the
  endpoint-selection fallback nor the pairing-URL branch. Per the design
  decision, the field stays in the contract: the Rust server never sends
  `AdvertisedEndpoint` at all (`PARITY-LEDGER.md:197`), and pulling on that
  thread is the separate, larger question this ticket scopes out.
- **`ChatHeader.test.ts`'s "hosted static mode" case was renamed, not deleted.**
  Only the name mentioned hosted mode; `shouldShowOpenInPicker` just takes
  `primaryEnvironmentId: null`.

### Left alone deliberately

`packages/shared/src/remote.ts` keeps its own `readHostedPairingRequest` and the
`"hosted-pairing-host"` error source. It is a separate implementation from the
deleted `apps/web` one, it backs `resolveRemotePairingTarget`, which ticket 73
needs, and `packages/` was not in this ticket's scope. Worth a follow-up once 73
has settled what the remote path actually looks like.
