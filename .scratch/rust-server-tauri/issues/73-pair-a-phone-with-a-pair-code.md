# 73 — Pair a phone with a pair code

> _This was generated by AI during a design conversation, 2026-07-29._

**What to build:** the server half of pairing — mint a code, trade it for a
token, verify that token at the socket upgrade — plus an origin allowlist, so a
phone reaching this machine through a tunnel can connect and a stranger cannot.

**Status:** ready-for-agent

**Depends on:** 72 (removes the hosted path; this ticket keeps the local one)

## Why

The user wants to drive laplus from their phone, with the PC reached over
`cloudflared` or Tailscale. Today that fails, and the failure is not where you
would expect. The tunnel handles reachability fine — `cloudflared` runs _on this
machine_ and dials `127.0.0.1`, so the loopback bind is not in the way. The page
loads. Then the socket upgrade 401s, because the browser sends
`Origin: https://…trycloudflare.com` and `auth::authorize` refuses any host that
is not loopback (`auth.rs:178`).

Relaxing that check alone would be worse than leaving it. `auth::authorize`
**verifies no credential at all** and accepts an absent one, which is safe
exactly because loopback is the boundary. Punch a tunnel through the boundary
and any stranger who reaches the URL gets a shell running as the user. So the
origin check and real credential verification have to land together. `docs/adr/0015`
is the decision this ticket revisits; it should be superseded, not quietly
contradicted.

## Read the reference first

`reference/t3code-server/src/auth/` is the specification and it is smaller than
its line count suggests — most of the 5,100 lines are DPoP, OAuth scopes, client
session management and relay tracing, none of which this needs. The parts that
matter:

- **`PairingGrantStore.ts:260-263`** — the code format. Twelve characters from
  `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`: no `0`/`O`, no `1`/`I`/`L`, because a human
  reads this off one screen and types it into another. Rejection-sampled against
  `PAIRING_TOKEN_REJECTION_LIMIT` so the distribution is uniform — copy that, a
  bare `% 32` biases the first eight letters.
- **`PairingGrantStore.ts:241`** — 5-minute TTL for a user-facing code.
- **`PairingGrantStore.ts:437-568`** — `consume`. Attempts an atomic
  `consumeAvailable` first and only diagnoses _why_ on a miss, so two
  simultaneous redemptions cannot both succeed. The ordering is the point.
- **`persistence/Migrations/020_AuthAccessManagement.ts`** — the whole schema, 42
  lines: `auth_pairing_links` and `auth_sessions`.
- **`auth/http.ts:254-385`** — the endpoint handlers.
- **`auth/EnvironmentAuth.ts:941-957`** — upgrade verification. `wsTicket` first,
  then the header, then the cookie: the same precedence `auth.rs` already records.
- **`auth/SessionStore.ts:403-404`** — 30-day sessions, 5-minute WebSocket tickets.

## The chain

| step                  | endpoint                            | lifetime   |
| --------------------- | ----------------------------------- | ---------- |
| mint a code           | `POST /api/auth/pairing-credential` | 5 min      |
| trade code for token  | `POST /oauth/token`                 | 30 days    |
| token → socket ticket | `GET /api/auth/websocket-ticket`    | 5 min      |
| open the socket       | `/ws?wsTicket=…`                    | connection |

The client half of all four is **already written and waiting** —
`packages/client-runtime/src/authorization/remote.ts:35-98` and
`connection/onboarding.ts:86-128`. Nothing in `apps/web` or `packages/` should
need to change for the happy path. If it does, that is a finding worth writing
down rather than a licence to edit the client.

## The constraint that will bite

**The desktop window must keep connecting with no credential at all.** It sends
none today (`auth.rs:59-62` — `Credential::Absent`, accepted deliberately), and
the moment the upgrade starts verifying, the window is the first thing to break.

Upstream's answer is at `PairingGrantStore.ts:314-330`: seed an in-memory grant
at boot with `remainingUses: "unbounded"` and a 24-hour TTL, handed to the
renderer over a trusted channel. laplus can be simpler, because the shell and the
server are one process — but the shape is the same, and the rule that falls out
of it is:

> **A loopback origin keeps the permissive posture. A non-loopback origin must
> present a credential that verifies.**

That keeps `docs/adr/0015`'s reasoning intact for the case it was written about
and adds a case it did not consider.

## Scope

**Server, `server/crates/laplus-server/`:**

1. Two tables in the existing SQLite database, following `020_AuthAccessManagement.ts`.
2. Code generation and `consume`, with the rejection sampling and the atomic
   single-use semantics from `PairingGrantStore.ts`.
3. Sessions: issue a bearer on exchange, verify it, expire it, revoke it.
4. WebSocket tickets: issue from a session, verify at the upgrade, 5-minute TTL.
5. Four routes, matching `EnvironmentAuthHttpApi` in
   `packages/contracts/src/environmentHttp.ts` — that contract is the wire, not a
   suggestion: `POST /oauth/token`, `GET /api/auth/websocket-ticket`,
   `POST /api/auth/pairing-credential`, `GET /api/auth/pairing-links` +
   `POST /api/auth/revoke-pairing-link`.
6. `auth::authorize` gains the rule above, plus a configured allowlist of extra
   origins so the tunnel hostname can be named. Config, not a compile-time constant.
7. `/api/auth/session` stops hardcoding `authenticated: true` for remote callers,
   and `auth.bootstrapMethods` stops being empty — it should say `one-time-token`,
   which is what makes `PairingRouteSurface`'s copy read correctly
   (`PairingRouteSurface.tsx:310-323`).

**Web:** ideally nothing. `/pair` and the Settings pairing panel go live on their
own once the endpoints answer.

## Out of scope

- **DPoP** (`auth/dpop.ts`). Browsers do not use it here.
- **OAuth scopes.** This server enforces none; accept the `scope` parameter,
  record it, do not gate on it. Say so in the module doc so the next reader knows
  it was a decision.
- **CORS.** Only the hosted app needed it, and 72 removes that. Over a tunnel the
  phone is same-origin.
- **Client session listing and revocation** (`auth.clients`, `auth.revokeClient`).
  Nice, not load-bearing. Leave the UI refusing.
- **Making the server bind off-loopback.** The tunnel runs locally and does not
  need it. Keeping the bind is a second lock on the door.

## Decisions to make, and a recommendation

- **Store the code in plaintext or hashed?** The reference stores plaintext
  (`020_…ts:10`) so Settings can re-display an active link for re-copying.
  Recommendation: follow it. The codes live five minutes, the database is already
  full of the user's conversations, and a hash breaks the list-and-recopy UI for
  no threat this product faces. Record the choice either way.
- **Signed tokens or database rows for sessions and tickets?** Upstream signs
  with a secret from `ServerSecretStore.ts`. A row is simpler and makes
  revocation trivial. Recommendation: rows for sessions, and either for tickets.

## Testing

`server/CLAUDE.md` documents the discipline; this is the ticket to actually
follow it. Write the socket/conformance test before the implementation. Assert on
decisions, never on elapsed wall-clock. Run with `--no-fail-fast` and redirect to
a file rather than piping into `head`.

Cases that need to exist:

- a fresh code exchanges once and the second attempt fails
- an expired code fails
- a revoked code fails
- two concurrent redemptions produce exactly one grant
- a loopback origin with no credential still upgrades
- a non-loopback origin with no credential is refused
- a non-loopback allowlisted origin with a valid ticket upgrades
- a non-loopback origin that is _not_ allowlisted is refused even with a valid ticket
- `refusals.rs`'s prose counts still match after any RPC surface change (see the
  note in that module — the counts are correct now and move if the table does)

## Verify during implementation, not before

**What does a phone browser lose?** Features that reach `window.desktopBridge`
cannot work there — the bridge is how the Tauri shell exposes what a browser
cannot do. Nothing in the auth path touches it, so this does not block the
ticket, but it decides whether a paired phone is pleasant or quietly broken.
Nobody has driven the UI from a second origin, so this is unknown rather than
assumed-fine. Find the consumers, decide per feature whether the right answer is
a graceful disable or a refusal the user can read, and write down what you found.

## Comments

**This is the largest open ticket in the tracker and should not be taken in one
sitting.** Piece 6 alone (the origin rule) is shippable and useless without the
rest; pieces 1–4 are shippable and invisible. A sensible split is
storage-and-codes, then endpoints, then the upgrade rule last — the upgrade
change is the one that can lock the user out of their own window.

**Security note for whoever implements it.** Until this lands, do not tell the
user a tunnel is safe. A `trycloudflare.com` URL is the public internet, and
until piece 5 verifies something, the answer to "who can reach my terminals" is
"anyone with the URL". Cloudflare Access or a Tailscale-only tunnel is the
interim answer, and it stays good practice afterwards. **This is still true.**
The upgrade rule is the piece not yet built.

## Where this stands

Two of the three pieces the split above recommends are done.

**Storage and codes** — `src/pairing.rs` (new: what a credential is, the TTLs,
the record types, scope encoding), migration **v5** and nine `Database` methods
in `src/store.rs`, `Shell::database()` in `src/orchestration.rs`. Both 8-thread
race tests this ticket asks for are in `store.rs`.

**Endpoints** — the five routes, their handlers in `src/server.rs`, their bodies
and payload readers in `src/http.rs`, and `tests/http_pairing.rs`, which walks
the whole chain at the wire and ends with an open socket. `bootstrapMethods`
landed with them.

**The upgrade rule** — `src/auth.rs` settles the origin and reports what was
presented; `src/server.rs::authorized` verifies it against the store. An absent
credential is refused. `src/remote_access.rs` reads `remote-access.json` from
the preferences directory for the tunnel hostname. `docs/adr/0019` supersedes
`0015`.

**The window's boot grant** — `Database::issue_desktop_boot_grant`,
`Server::window_url`, and the shell opening
`http://127.0.0.1:4773/#token=…`. This is what replaced the window's exemption
from the credential check, and it is upstream's design reached by a different
channel; `docs/adr/0019` argues both.

810 tests pass across 31 binaries, `cargo test --no-fail-fast --offline` exit 0.

**Remaining: driving the window**, and the `window.desktopBridge` audit under
"Verify during implementation". A green suite is not evidence and this is the
change most able to lock the developer out of their own window.

The open decision, now made: **the origin allowlist is a `remote-access.json`
in the preferences directory.** `config.rs:350-358` argues explicitly against an
environment variable for anything the suite touches and establishes
`ServerConfig::detect_in(data_dir)` as the seam instead; a user who
double-clicks `laplus.exe` has no shell in which to export one anyway, which is
the case this whole ticket is for. See Findings 7 for why an unparseable file is
logged rather than reported as a `ConfigIssue`.

## Findings — where this ticket is wrong and the code is right

### 1. The route table above is wrong in three places

The ticket says the contract "is the wire, not a suggestion" and then
contradicts it. From `packages/contracts/src/environmentHttp.ts:337-411`:

| this ticket says                     | the contract says                       |
| ------------------------------------ | --------------------------------------- |
| `POST /api/auth/pairing-credential`  | `POST /api/auth/pairing-token`          |
| `POST /api/auth/revoke-pairing-link` | `POST /api/auth/pairing-links/revoke`   |
| `GET /api/auth/websocket-ticket`     | **`POST`** `/api/auth/websocket-ticket` |

`GET /api/auth/pairing-links` and `POST /oauth/token` are right.
`packages/client-runtime/src/authorization/remote.ts:81-98` confirms the client
POSTs for a ticket. The contract was followed.

### 2. "A bare `% 32` biases the first eight letters" is false

Line 42. The alphabet is 32 characters and a byte has 256 values; 32 divides
256 exactly, so `% 32` is already uniform, and upstream's
`PAIRING_TOKEN_REJECTION_LIMIT` computes to **256** — it rejects nothing.

The rejection sampling is implemented anyway, for the reason that does hold: it
stops being a no-op the moment someone shortens the alphabet, and it would fail
silently. `pairing.rs` says so and
`nothing_is_rejected_while_the_alphabet_divides_the_byte_range` pins it.

Related: **`L` is in the alphabet**, though `0`, `O`, `1` and `I` are not.
Dropping a fourth character would leave 31, which does not divide 256.

### 3. The schema to copy is migration 031, not 020

Line 48 cites `020_AuthAccessManagement.ts`. `031_AuthAuthorizationScopes.ts`
drops and recreates both tables to replace `role` with `scopes`, and is the
shape upstream actually runs. 021, 022 and 032 add client metadata, a
`last_connected_at` and a DPoP thumbprint on top.

### 4. `/oauth/token` is form-urlencoded

`AuthTokenExchangeRequest` ends `.pipe(HttpApiSchema.asFormUrlEncoded())`
(`contracts/src/auth.ts:184`). Not JSON. `axum`'s `Form` extractor was rejected
deliberately: it answers a body it cannot decode with its own 422, and every
refusal this server makes has to be in the contract's shape or the client logs
a generic warning instead of the reason. Hence `http::form_fields`.

### 5. `revoke` has no 400 to refuse with

`EnvironmentScopedOperationErrors` gives `/api/auth/pairing-links/revoke` a 403
and a 500 and no `EnvironmentRequestInvalidError`, so a body that will not parse
cannot be answered with a 400 — the client cannot decode that status on that
route. It is answered with the 500 and the real cause goes to the log.
`/api/auth/pairing-token` declares the 400 and uses it.

### 6. The upgrade rule this ticket proposes does not hold

> A loopback origin keeps the permissive posture. A non-loopback origin must
> present a credential that verifies.

**This is bypassed by not sending an `Origin` header.** The check lived inside
`if let Some(origin)`, so a request carrying none was accepted unconditionally —
and a browser only sends `Origin` on WebSocket upgrades and non-`GET` requests,
so an absent one means a client that is not a browser. `curl` sends whatever it
likes. Before a tunnel existed that was fine, because loopback was the boundary.

**And "loopback" cannot be detected anyway.** `cloudflared` runs on this machine
and dials `127.0.0.1`, so a tunneled request arrives with the same peer address
as the window's. Nothing at the HTTP layer distinguishes them.

The rule that replaced it is upstream's: every request presents a credential
that verifies, no exemptions, and the window carries one. `docs/adr/0019`.

The ticket's premise — "laplus can be simpler, because the shell and the server
are one process" — is what led it astray. Being one process is exactly what
denies laplus the trusted channel Electron's preload gives upstream: the window
gets its page over HTTP from this same server, so anything baked into that page
is available to anyone who can make an HTTP request. The URL **fragment** is the
way out, because a fragment is never sent to the server.

### 7. `ConfigIssue` cannot report a bad `remote-access.json`

The obvious home for "your remote-access file will not parse", and it is not
available. `ServerConfigIssue` in the contract is a closed union of two
`keybindings.*` literals (`config.rs:158-172` spells this out), so a `kind` of
this server's invention would fail the client's decode of the **whole**
`server.getConfig` payload and the application would not open. `crate::settings`
hit the same wall and answered it the same way: complain to the log, keep the
safe default. The safe default is an empty allowlist, so a typo means a phone
that cannot connect rather than a machine that admits everybody.

### 8. `/api/auth/browser-session` is missing from the Scope list

Scope item 5 names four routes and calls the contract "the wire, not a
suggestion". It omits the route the desktop window and a same-origin phone both
actually use.

The ticket points at `packages/client-runtime/src/authorization/remote.ts` as
"the client half, already written" — and that file is the **remote** half, for a
client that added this machine as a second backend. The primary half is in
`apps/web/src/environments/primary/auth.ts:231-240`, and it reaches for
`client.auth.browserSession`, which trades a pairing code for a session cookie.
Implemented, because without it the window cannot boot.

## Decisions made while building, not to relitigate

- **Rows, not signed tokens**, for sessions _and_ tickets. This ticket
  recommended rows for sessions and "either" for tickets. A row makes revocation
  one `UPDATE` and needs no secret to keep.
- **A third table, `auth_websocket_tickets`.** Upstream has none because it signs
  its tickets. The `session_id` foreign key is what makes revoking a session take
  its outstanding tickets with it rather than leaving five minutes of them live.
- **Plaintext, for pairing codes and session tokens both.** This ticket
  recommended plaintext for codes and did not consider the token. Reasoning is in
  the migration comment: the database already holds every conversation and
  transcript, so an attacker who can read it does not need the bearer.
- **Scopes are recorded and never enforced**, per this ticket — but the
  _vocabulary_ is closed. A scope outside the contract's eight is refused with
  `invalid_scope` at both `/api/auth/pairing-token` and `/oauth/token`, matching
  the reference server (`auth/http.ts:262-278`). That is not enforcement: it is
  that `AuthEnvironmentScope` is a literal union on the client, so a pairing link
  carrying an unknown scope back fails the decode that renders the whole Settings
  panel. A `scope` asking for something the code did not grant is
  `scope_not_granted`, also upstream's (`EnvironmentAuth.ts:697-700`).
- **One dependency added: `getrandom` 0.3.** Neither source already in the tree
  is fit for a credential — `RandomState` (`auth.rs:235`) is a hash seed, and
  SQLite's `randomblob()` is seeded on Windows from the system time, the process
  id and the tick count. Reasoning is in `server/Cargo.toml`.
- **Types in `pairing.rs`, SQL in `store.rs`**, mirroring how `store.rs` already
  takes `Project` from `projects.rs` and `Activity` from `threads.rs`.
- **`Rejection` grew a `reason`**, so the routes can say `missing_credential`
  where nothing was presented and `invalid_credential` where something was and
  did not verify. `authorize`'s own refusals still say `invalid_credential`, for
  the reason `Rejection::body` gives.
- **The window's boot grant is re-usable; a phone's code is not.** The window
  re-reads its credential out of the address bar on every page load, so a
  strictly single-use grant would let the developer press F5 once and then lock
  themselves out. Upstream's `remainingUses: "unbounded"`, narrowed to the one
  case that needs it. Exempt from _spending_, not from revocation or expiry —
  and `revoke_pairing_link` needed the same exemption, or stamping the grant on
  first use would have made the longest-lived credential the one nothing could
  withdraw. There is a test; it caught that.
- **The boot grant carries administrative scopes** and is filtered out of
  `active_pairing_links` by subject — upstream's
  `listPairingLinks({ excludeSubjects })`. Offering the window's own credential
  in a list headed "codes you can give a device" invites the developer to hand
  it out, or to revoke it wondering what it was.
- **The upgrade's 401 no longer carries `Access-Control-Allow-Origin: *`.**
  Upstream sets it, and did so when the only reason to refuse was the origin.
  Now the ordinary refusal is a credential that did not verify, and echoing `*`
  would let any page on any origin read the 401 it provoked.
- **The test harness pairs itself the way the window does**, through the real
  routes against the real store, rather than being handed a credential by a
  test-only seam. Two hundred tests run behind that, and a harness that reached
  around the policy would be two hundred tests quietly proving the wrong thing.
