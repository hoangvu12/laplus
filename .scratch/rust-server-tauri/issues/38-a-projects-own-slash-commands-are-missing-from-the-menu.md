# 38 — A project's own slash commands are missing from the menu

**What to build:** the `/` menu offering the commands a project keeps in its own
`.claude/commands`, as well as the built-ins and the developer's.

**Status:** ready-for-agent

**Found by:** `a89885662`, which states the gap in `crate::catalogue`'s header
rather than leaving it to be discovered. Not a regression — the menu was empty
before that commit.

## What happens

`crate::catalogue` fills the two menus from two places. Skills are a `readdir`,
so every registered project is scanned and a project's copy wins. Commands cost a
whole process — a `claude` started to answer one `initialize` request — so the
handshake happens **once**, wherever the server itself is running, and yields the
built-ins and the developer's user-scoped commands.

A `claude` reads `<cwd>/.claude/commands` for the directory it was started in.
The handshake's cwd is the server's, which is nobody's project. So a command a
repository ships for itself is absent from the picker.

Typing its name still works. The menu is a list of things to type and the CLI is
what expands them, so this costs discoverability rather than capability.

## Why it was left

This server has a _registry_ of projects rather than one project, and the
cheapest correct fix — a handshake per registered root — is a `claude` process
per project on every provider refresh, including at startup. That is a real cost
paid by everyone for a menu, and it scales with how many projects a developer has
registered rather than with how many they use.

## What to settle before starting

- **Is it per project, or per _active_ project?** The provider snapshot is one
  object for the whole server and the menus read it directly, so there is nowhere
  in the current shape to put "the commands for the project this pane is open
  on". Making the catalogue per-project is a contract-shaped question, not a
  scan-shaped one.
- **Is a handshake per root affordable if it is lazy?** Once per project per
  server run, on first use of that project rather than at startup, is a much
  smaller claim than the one rejected above and might be the whole answer.
- **Or is the disk enough?** A project's commands _are_ files — `.claude/commands/**.md`
  — unlike the built-ins, which is why skills work this way already. Scanning
  them would need this project to reimplement the CLI's own naming and
  frontmatter rules, and to keep up with them, which is the argument the
  handshake exists to avoid. It is still cheaper than a process.

## Acceptance

Deliberately not written until one of the three is chosen.

What can be said regardless:

- A project with a `.claude/commands/foo.md` offers `/foo` while that project's
  conversation is open.
- Startup does not gain a process per registered project.
- The built-ins and the user-scoped commands keep working exactly as now, on a
  machine with no project registered at all.

## Comments

### 2026-07-28 — triage. The cost premise is disproved; this is now ready work

> _This was generated by AI during triage._

**Status moved `needs-triage` → `ready-for-agent`.** This ticket was parked on a
cost objection, and the 2026-07-28 parity audit measured that objection against
the real binary and found it does not apply.

`.scratch/rust-server-tauri/2026-07-28-cli-stream-audit/03-project-scoped-commands.ndjson`
is a turn run in a scratch directory whose only distinguishing feature is
`.claude/commands/zzz-probe-marker.md`. Its `init` line lists **79 slash commands,
including `zzz-probe-marker`.**

So:

- The "a probe per project would be a `claude` per project on every refresh"
  objection is true **of a probe**. It is not true of a turn — the commands arrive
  **free** on the `init` of any real turn in that project, at no extra process
  cost at all.
- **`InitEvent` already declares `slash_commands`.** The field is parsed today and
  read by nothing. This is closer to wiring than to building.
- `crate::catalogue`'s separate objection — that init is not written until the CLI
  has been given a prompt — is what rules init out for the **handshake**, and does
  not apply to a turn.

**Of the three options in "What to settle", none is the answer, because the real
trade is the fourth thing the catalogue's own header names:** the handshake
returns objects with descriptions and argument hints; `init` returns bare names.
So the answer is neither source alone — it is the **union**: the handshake's rich
built-ins, plus each project's command names learned from the first turn run there.

### Acceptance, now writable

- [ ] A project with `.claude/commands/foo.md` offers `/foo` in the menu once a
      turn has been run in that project.
- [ ] The built-ins keep their descriptions and argument hints — learning project
      names does not flatten the rich entries to bare names.
- [ ] Startup gains no process per registered project, and no provider refresh
      does either.
- [ ] A machine with no project registered still gets the built-ins and the
      user-scoped commands, exactly as now.
- [ ] A project whose commands change on disk between turns picks up the change on
      the next turn's `init` — or, if the learned set is cached per session, that
      is stated.
- [ ] What happens **before** the first turn in a project is decided and stated: a
      menu missing project commands until the first prompt is defensible, but it
      should be a choice rather than a surprise.

### Out of scope

- Scanning `.claude/commands/**.md` from disk. That was option three and the audit
  makes it unnecessary — it would mean reimplementing the CLI's naming and
  frontmatter rules and keeping up with them, which is the argument the handshake
  exists to avoid.
- Skills, which already work by `readdir` and are unaffected.
