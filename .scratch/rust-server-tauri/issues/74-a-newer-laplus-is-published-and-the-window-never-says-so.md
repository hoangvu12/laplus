# 74 — A newer laplus is published, and the window never says so

> _This was generated by AI during a design conversation, 2026-07-29._

**What to build:** the update path an installed laplus has no way to take —
check a published release, download it, install it — behind the update pill the
UI already draws.

**Status:** ready-for-agent

**Depends on:** ADR-0020 and `.github/workflows/release.yml`, which is where the
release being checked for comes from. Nothing here works before a first tag.

## Why

Ticket 66 decided the shape and left the build. `docs/adr/0020` records the
release half; this is the half that lets an installed copy notice.

The awkward part, and the reason this is a ticket rather than a plugin line:
**the UI for this is already written and neither of its two entry points can
appear.** Ticket 66's "Where this stands" has the detail; in short:

- `SidebarUpdatePill` and `state/desktopUpdate.ts` read `window.desktopBridge`,
  which is Electron's preload and is always `undefined` here.
- `ServerUpdateAction` renders only inside a `versionMismatch` block, and
  ADR-0011 removed version drift by construction.

So publishing a release lights up nothing on its own, and the fix is not "flip
`serverSelfUpdate` to true" — that produces a button that never renders.

## The rule this follows

> **The pill is the surface. It is fed by Tauri, not by a bridge that does not
> exist, and not by pretending two halves of one binary disagree.**

`window.desktopBridge` stays `undefined`. Several other features branch on that
object — `ConnectionsSettings.tsx` in a few places, `branding`, `browser` — and
defining a partial one to satisfy the pill would tell all of them a full Electron
bridge is present. That is a worse bug than no update button, and it is why this
does not simply shim the global.

What changes instead is the two readers. `state/desktopUpdate.ts` and
`SidebarUpdatePill.tsx` ask a laplus module for the update bridge; that module
answers with a Tauri-backed implementation in the window, and `undefined`
everywhere else — a phone browser included, which is the correct answer there.

## What was established before writing this, and should not be re-derived

**Remote IPC already works here.** The window is pointed at
`http://127.0.0.1:<port>` (ADR-0010), so its page is `Origin::Remote` to the
IPC, and `capabilities/titlebar.toml` already grants that origin the six
`core:window` commands the titlebar presses. This ticket adds permissions to
that same mechanism; it does not invent one.

**Plugin commands, not custom `#[tauri::command]`s.** From `tauri-2.11.5`'s
`webview/mod.rs:1818` and its own comment — "This ensures remote content can
never reach custom commands unless an explicit `remote` capability has been
configured for them" — a custom command from a remote origin is refused unless
the app ships an ACL manifest naming it. `tauri-plugin-updater`'s commands come
with permissions already defined, exactly as `core:window`'s do. Taking the
plugin's commands is therefore less machinery _and_ the path the ACL was built
for.

**No `@tauri-apps/*` npm dependency.** `desktopShell.ts` already argues this for
`isTauri`, and the argument holds here for a different reason: the web bundle is
80% of the artifact (ticket 24), and what the packages would buy is a `Channel`
class that is fifteen lines. Its wire format is fixed and observable —
`window.__TAURI_INTERNALS__.transformCallback(handler)` returns an id, the object
serialises as `` `__CHANNEL__:${id}` ``, and `unregisterCallback(id)` releases
it (`tauri-2.11.5/scripts/bundle.global.js`).

**The plugin's download command requires the channel.** `plugin:updater|download`
and `|download_and_install` both take `onEvent` as a required argument, so the
channel is not optional and "skip progress for now" is not available.

## Scope

**`server/crates/laplus-shell/`:**

1. `tauri-plugin-updater` as a dependency, registered in the builder.
2. `tauri.conf.json`: `bundle.createUpdaterArtifacts`, and a `plugins.updater`
   block naming the public key and the endpoint.
3. A capability granting the updater's commands to the loopback origin. Whether
   it joins `titlebar.toml` or gets its own file is the implementer's call, but
   `the_capability_covers_the_origin_the_server_serves` must cover whatever is
   added, for the reason that test already gives: a missing grant is a control
   that silently does nothing.

**`apps/web/`:**

4. A module that produces a `DesktopUpdateState` from the plugin's commands: the
   status machine, the download channel, the version and the error contexts.
   `packages/contracts/src/ipc.ts:192` is the shape and is not negotiable —
   the pill reads every field of it.
5. `state/desktopUpdate.ts` and `SidebarUpdatePill.tsx` read that module instead
   of `window.desktopBridge`.

**`.github/workflows/release.yml`:**

6. `TAURI_SIGNING_PRIVATE_KEY` in the build environment, and `latest.json`
   generated and attached to the release, since that is what the endpoint points
   at.

## Out of scope

- **The `nightly` channel.** `DesktopUpdateState` carries one and the tooltip
  renders release notes for it; this fork publishes one channel (ADR-0020), so
  report `latest` and leave the notes empty.
- **`setUpdateChannel` and `checkForUpdate` as user-facing controls.** The pill
  never calls them. Implement them or refuse them, but no UI is owed one.
- **The arm64/Rosetta warning.** Windows-only fork; report `x64` honestly and the
  warning never fires.
- **`server.updateServer` and `capabilities.serverSelfUpdate`.** This is the
  shell updating the application, which is not the RPC method's meaning — that
  one is a server updating itself for a client that is elsewhere. Leave the
  capability false and the method refusing.
- **Authenticode.** Unsigned installers warn; ADR-0020 records it.

## The thing that will bite

**The signing key is not recoverable.** `tauri signer generate` makes a keypair;
the public half goes in `tauri.conf.json` and ships inside every installed copy.
An installed laplus will only accept an update signed by the matching private
half — so losing that key strands every existing install permanently, and the
only way out is asking people to reinstall by hand. It belongs in the
maintainer's password manager and in `TAURI_SIGNING_PRIVATE_KEY` as a repository
secret, and in nothing else. It must never be committed.

The second-order version: **do not regenerate the key** once anything has been
published with it.

## Acceptance criteria

- [x] `window.desktopBridge` is still `undefined` in the window, and nothing new
      reads it
- [ ] The pill appears in the window when the endpoint offers a newer version,
      and its download → restart-to-update path completes an install
      — **unmet, and needs a published release to be met at all.** Nothing has
      been tagged, so there is no newer version for a check to find.
- [x] The pill never appears in a phone browser, because the bridge resolves to
      `undefined` off the desktop shell — `has no bridge where there is no Tauri
    window`
- [x] The capability covers the origin the server actually serves, asserted the
      way the titlebar's grant already is
- [x] A refused command says so in the console rather than failing silently,
      matching `invokeWindowCommand`'s reasoning
- [~] `latest.json` is on the release and names the artifact the workflow built
  — the generation was run by hand against a real signature and produces a
  manifest naming the file that signature covers. What is unproven is the
  workflow step running it, since no release has been cut.
- [x] The private key is in no committed file, and `.gitignore` says so
- [x] `cargo test --no-fail-fast` passes from `server/`, and the TypeScript
      suites pass
- [ ] The window is driven and the pill actually pressed — a green suite is not
      evidence, and this ticket's whole surface is a button

## Where this stands

Built, and unverified in the one way that counts — see the last criterion.

**The shell** registers `tauri-plugin-updater` and grants its `check`,
`download` and `install` commands to the loopback origin through
`capabilities/updater.toml`, a second capability file beside the titlebar's.
`tauri.conf.json` carries `createUpdaterArtifacts`, the public key and the
endpoint. `the_page_may_check_for_download_and_install_an_update` asserts the
grant against the address the server actually serves, the way ticket 27's does.

**The page** drives it from `apps/web/src/shellUpdate.ts`: the status machine,
the download channel and the two resource ids, over a `Invoke` and a channel
factory that a test can substitute. `state/desktopUpdate.ts` and
`SidebarUpdatePill.tsx` read it instead of `window.desktopBridge`, which stays
`undefined`. Twelve tests in `shellUpdate.test.ts`, including that a browser
with no Tauri internals gets no bridge at all.

**The release** signs what it builds and writes `latest.json` from the signature
file rather than by hand, so the manifest cannot name an artifact the release
does not carry. A tag with no `TAURI_SIGNING_PRIVATE_KEY` secret is refused with
a sentence before the build rather than a signing error inside it.

### Three things found while building, worth not rediscovering

1. **`serde_json` became a runtime dependency of `laplus-shell`.** Adding a
   `plugins` section to `tauri.conf.json` makes `tauri::generate_context!`
   expand plugin configuration into `serde_json` paths at the call site. The
   crate uses it nowhere else and cannot drop it; the failure without it names
   the macro rather than the reason, which is why it is written down beside the
   dependency.

2. **`plugins.updater.windows.installMode` trips ticket 30's guard.**
   `xtask::install::redirected` matches `"installMode"` against the whole of
   `tauri.conf.json`, because the setting it exists to catch —
   `bundle.windows.nsis.installMode` — would undo the patch that keeps the
   installer off the developer's database. The updater's key of the same name is
   about how an update presents itself while it runs and is unrelated. **The
   setting was dropped rather than the check narrowed**: its value there was the
   default anyway, and a guard on where somebody's database lives is not the
   thing to make cleverer for a convenience. `Astray::InstallModeChanged` now
   documents the near-miss.

3. **Every release build now needs the key**, local ones included.
   `createUpdaterArtifacts` means the bundler signs, and it fails without one.
   `README.md` and `server/CLAUDE.md` both say so, because a developer running
   `cargo xtask release` on a fresh clone will otherwise meet it as a puzzle.

### The size cost, measured rather than estimated

A signed release was built locally to check that any of this produces what the
workflow expects. It does: `laplus_0.1.0_x64-setup.exe` **and**
`laplus_0.1.0_x64-setup.exe.sig` land in `target/release/bundle/nsis/`, which is
what `latest.json` is generated from. Running that generation step by hand
against the real signature produced a manifest whose URL matches the file the
signature's own trusted comment names.

The plugin brings `reqwest`, `rustls` and `zip`, none of which the artifact
carried before, and they are not free:

|                                 | before   | after        |          |
| ------------------------------- | -------- | ------------ | -------- |
| Installer (NSIS)                | 5.06 MB  | **5.82 MB**  | +0.76 MB |
| Application binary              | 24.26 MB | **26.86 MB** | +2.60 MB |
| Headroom in the 20–30 MB target | 5.74 MB  | **3.14 MB**  | −2.60 MB |

**Still inside the target, and the headroom is now less than half of what it
was.** That is the number to watch: the next dependency of this size is the one
that ends the project's central claim, and `docs/artifact-size.md` is rewritten
by every release build so it cannot be missed.

Those are the binary's figures, which is the only like-for-like row here. **The
committed report's "installed on disk" line got weaker in this change and should
not be read as a regression in the artifact**: the previous one was measured by
`--measure-install`, which installs, weighs and uninstalls, and this build was
run without it because installing laplus on the developer's own machine is not
something to do unasked. The release workflow passes that flag, so the
install-measured figure returns on the first release and the file corrects
itself.

## Comments

**This is testable further than it looks.** The state machine is a pure function
from plugin responses to `DesktopUpdateState` and belongs in a `.logic.ts` with a
suite, the way `desktopUpdate.logic.ts` already is. What genuinely needs the
window is the last criterion.

**An unreachable endpoint must not become a recurring visible error** — ticket
66's standing requirement. A failed check is `status: "error"` with
`errorContext: "check"`, which the pill does not render at all, and that is the
correct behaviour rather than an oversight.
