# 41 — Changing the model mid-thread stops the next message from sending

> _This was generated by AI during triage._

**What to build:** the three thread-setting commands the client sends before every
turn, so that a turn dispatched after a picker change is not blocked by their
refusal.

**Status:** ready-for-agent

**Found by:** the 2026-07-28 parity audit, ledger §0; scope corrected by the
decider audit §1 (`.scratch/rust-server-tauri/2026-07-28-decider-audit.md`).

## What happens

Send a message. Change the model or the permission mode in the composer. Send
another. The second one **bounces** — an error appears and the text reappears in
the box.

The path:

1. The client's `persistThreadSettingsForNextTurn` fires `thread.meta.update`,
   `thread.runtime-mode.set` or `thread.interaction-mode.set` — but **only when
   the value differs from what the server holds.** That is why leaving the
   pickers alone works, and why the suite and every session so far missed it.
2. `crate::orchestration` refuses all three by name:
   `Command not implemented by this server: …`.
3. The client records that as `failure` and guards the turn start on
   `failure === null`. `thread.turn.start` is never dispatched.
4. The prompt is put back in the composer and a thread error is set.

Same guard, second path: the client auto-titles from the first message via
`thread.meta.update` when `isFirstMessage && isServerThread`. A new conversation
normally starts as a **draft** (the title arrives in `bootstrap.createThread`), so
this is likely unreachable today — but it is one code path away from being live.

## The fix is smaller than it looks

Upstream's `thread.turn.start` **ignores the mode on the command** and reads the
thread's stored values. That is why its client persists first and treats a setter
failure as fatal: on that side these commands are the only route by which a mode
reaches a turn.

laplus reads all three off the command instead (`StartTurn`, with an explicit
"absent means whatever the thread already had"), and `crate::threads` applies them
to the thread row. **So the mode already works here.** These handlers are needed
only so the client's pre-flight succeeds.

Three handlers that write the thread row and publish their events restore the send
path. The turn keeps taking its mode from the command as it already does. There is
no ordering problem to solve and no new state to keep — and laplus's route is the
more robust of the two, because the mode cannot be lost by a setter that failed.
Do not "fix" it toward upstream's.

## Key interfaces

- `thread.meta.update` — carries `title`, `colour` and other metadata. Note it
  also carries `scripts` for projects' sibling command; see 48, which is a
  different command with the same shape of gap.
- `thread.runtime-mode.set`, `thread.interaction-mode.set` — single-field writes.
  `crate::threads` already applies `interaction_mode` from an `Option`, so the
  setter is nearly there.
- Each must publish the corresponding event (`thread.meta-updated`,
  `thread.runtime-mode-set`, `thread.interaction-mode-set`) so the client's
  optimistic state settles.

## Acceptance

- [ ] Send a message, change the model, send another — the second sends.
- [ ] Same for the runtime-mode and interaction-mode pickers.
- [ ] The thread row reflects the new value, and it survives a restart.
- [ ] A turn started with an explicit mode on the command still uses that mode;
      the command remains the authority, not the row.
- [ ] Renaming a thread through `thread.meta.update` persists and appears in the
      sidebar.
- [ ] A regression test drives a picker change followed by a send. The reason this
      shipped is that no test changed a picker between two messages.

## Out of scope

- Plan mode actually reaching the CLI — that is 47, and it is a real gap rather
  than a bookkeeping one.
- Auto-titling by an LLM (spec exclusion).
