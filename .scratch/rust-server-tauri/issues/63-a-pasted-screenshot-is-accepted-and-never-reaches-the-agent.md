# 63 — A pasted screenshot is accepted and never reaches the agent

> _This was generated by AI during triage._

**What to build:** attachments — which needs `assets.createUrl` and somewhere to
put the bytes, and that is a design question rather than a handler.

**Status:** needs-triage

**Found by:** the 2026-07-28 parity audit, ledger M7; scope sharpened by surface
walk §S6.

## What happens

The developer pastes a screenshot into the composer. It is accepted. It is then
**dropped on the way to the agent** in `crate::orchestration`, silently.

Silent is the worst version of this. A refusal would at least tell the developer
their image is not going anywhere; instead they send a message about "this error"
with an image the agent cannot see, and get a confused answer.

The surface walk found the scope is wider than "attachments are dropped":
**`assets.createUrl` is called at boot**, not on demand — so the method is refused
on the first screen, before anything is attached.

## Why this is not ready work

Three questions have to be answered before code:

**1. Where do the bytes live?** Upstream has an asset URL service. laplus has a
SQLite database and a profile directory. Options: blobs in SQLite, files in the
profile directory with a table of references, or a temp directory with a lifetime.
Each has a different answer to "what happens on delete" and "how big can this get".

**2. What is the lifetime?** An image pasted into a conversation is referenced by
the transcript. If the transcript survives a restart — it does — then so must the
image, which rules out anything temporary. If a conversation is deleted (49), the
images should go with it, which means this has to be part of that cleanup.

**3. How does it reach the agent?** The CLI takes images in a message's content
blocks. Whether laplus should inline base64 into the `stream-json` it writes on
stdin, or write a file and pass a path, is a protocol question that should be
answered against the **real binary** before either is built — this project has
already been caught once assuming an SDK capability the CLI does not expose
(see 62). One capture settles it.

## The spec tension, which is the reason this is triage and not a build

The spec names **"asset URL service, external diagnostics, process management"**
as out of scope. But attachments are the part of that block with a real user cost,
and the ledger flags exactly this: M7 overlaps a spec exclusion and is the piece of
it worth reconsidering.

**So the decision to take is whether attachments are in scope for v1 at all.** If
yes, the exclusion needs narrowing to say so — the asset _service_ is excluded,
attachment _storage_ is not. If no, then the composer should stop accepting
images, because accepting and dropping is worse than refusing.

That is a maintainer's call, and it is why this is `needs-triage`.

## Acceptance

Deliberately not written; it depends on the answer above.

What can be said regardless:

- The developer is never told an attachment was accepted when it was not.
- `assets.createUrl` stops producing a refusal at boot, whichever way the decision
  goes — see 46 and 39 for the two shapes of "refuse honestly".
