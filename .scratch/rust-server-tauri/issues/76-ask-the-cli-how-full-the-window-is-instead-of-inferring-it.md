# 76 — Ask the CLI how full the window is, instead of inferring it

> _This was generated by AI while finishing ticket 40, 2026-07-29._

**What to build:** the `get_context_usage` control request, so the context meter
reads what the CLI says about the window rather than what this server works out
from the token counts flowing past.

**Status:** ready-for-agent

**Depends on:** ticket 40, which is done. This replaces the _source_ of the
reading; the activity, the payload and the client are already in place.

## Why

Ticket 40 filled the meter by inference: every reading is assembled from `usage`
counts on assistant messages, `message_delta`s and the terminal `result`, and the
window itself is scraped out of `modelUsage`. That works, and it leaves three
things wrong that no amount of further inference fixes.

**`compactsAutomatically` is unobtainable.** The client renders a line reading
"Claude automatically compacts its context when needed." from it. The CLI never
mentions auto-compact anywhere in the stream — all eighteen captures are silent —
so this server cannot fill the field and the sentence never appears. Compared
side by side against T3 Code on 2026-07-29, this was one of exactly two visible
differences in the tooltip.

**The first turn of a session has no percentage.** `modelUsage` arrives only on
the terminal `result`, so until a turn has finished the server knows a token
count and no window, and the client draws a bare figure with no percentage and no
bar. `SessionState::context_window` carries it forward afterwards, which fixes
every turn except the first.

**A turn that emits no counts gets no reading**, even when the conversation
plainly has a size — an interrupted turn, a turn that failed before the API was
reached. The meter keeps the previous value, which is right, but there is no way
to ask for the current one.

All three are the same shape: this server can only report what happens to go past
it, and there is a question it could ask instead.

## What upstream does

`reference/t3code-server/src/provider/Layers/ClaudeAdapter.ts`,
`queryCurrentContextUsage` (~line 1774). It calls `query.getContextUsage()` and
normalises the reply through `normalizeClaudeContextUsageApiSnapshot`:

```ts
makeClaudeTokenUsageSnapshot({
  activeTokens: value.totalTokens,
  contextWindow: value.maxTokens,
  compactsAutomatically: value.isAutoCompactEnabled,
});
```

So the reply carries `totalTokens`, `maxTokens` and `isAutoCompactEnabled` — the
whole reading in one answer, including the field that cannot be inferred.

Note the precedence upstream uses in `completeTurn`: the control-request snapshot
is preferred, and the counts-derived one is the **fallback** when the request is
unavailable or fails. Keep that order. An SDK that does not implement the request
must not lose the meter that ticket 40 built.

## Key interfaces

- `crate::protocol` — a new outbound control request beside
  [`interrupt_line`], and its `control_response` shape. The envelope is already
  understood in both directions: this server sends `interrupt` and answers
  `can_use_tool`, and `Acknowledgement` already models a reply that can refuse.
- `crate::turn` — where to ask. Upstream asks as a turn completes; asking once
  when the session announces itself would also fix the first-turn case, and is
  worth considering rather than copying the timing wholesale.
- `SessionState::token_usage` — the field the answer lands in. Its two remembered
  neighbours (`context_window`, `total_processed_tokens`) exist only to paper
  over not being able to ask, and may narrow once this works.

## The capture problem

**No fixture contains this exchange**, and one has to before the behaviour can be
tested. It is a request this server has never sent, so it is not in any recording
— `tools/wire-capture/` records the _socket_, not the agent, and the eighteen
`claude-cli` captures were taken from a server that never asked.

Getting one means sending the request against a real `claude` and recording the
reply. Worth checking first whether the installed CLI implements it at all: it is
an SDK control request, and the version this project drives may answer with an
error, which is itself the thing the fallback path has to survive.

## Acceptance

- [ ] The tooltip shows "…automatically compacts its context when needed." when
      the CLI says auto-compact is on, and does not when it says otherwise.
- [ ] The meter has a percentage on the **first** turn of a session, before any
      `result` has arrived.
- [ ] A CLI that refuses or does not implement the request still gets the
      ticket-40 meter, from the counts. No error reaches the conversation.
- [ ] A fixture under `server/fixtures/claude-cli/` contains the request and its
      reply, and the golden pins the reading taken from it.
- [ ] The reply is preferred over the inferred reading when both are available.
