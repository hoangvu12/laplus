# 39 — A refusal the client cannot decode, and the decoder's complaint is what the user reads

> _This was generated by AI during triage._

**What to build:** refusals that answer with an error tag the method actually
declares, so an unimplemented feature renders as an empty state rather than as a
schema error.

**Status:** done

**Found by:** the 2026-07-28 parity audit, surface walk §S2
(`.scratch/rust-server-tauri/2026-07-28-surface-walk.md`). Seen on screen, not
inferred.

## What happens

Open `/settings/diagnostics` or `/settings/source-control`. The page shows this,
verbatim:

```
Expected { readonly "_tag": "EnvironmentAuthorizationError", ... },
got {"_tag":"ServerMethodNotImplementedError","message":"Method not implemented
by this server: server.getProcessDiagnostics","method":"server.getProcessDiagnostics"}
at ["cause"][0]
```

`crate::rpc` answers every unimplemented method with a single
`ServerMethodNotImplementedError`. That tag is **not a member of the error union
those methods declare in the contract**, so the client cannot decode the _error_,
and what the developer is shown is the schema decoder complaining about the shape
of a refusal — not any statement about the feature.

Four methods are known to be affected: `server.getProcessDiagnostics`,
`server.getProcessResourceHistory`, `server.getTraceDiagnostics`,
`server.discoverSourceControl`. There may be more; see acceptance.

## Why this is worth doing independently of the features

None of these four methods is scheduled. Answering with a tag each one declares
turns four raw decoder errors into four honest empty states without implementing
anything. It is a change to how this server refuses, not to what it offers.

## The rule already exists in this codebase

`crate::config` reasons about exactly this for `ConfigIssue` — _"its `kind` is one
of two literals the contract names, not a label: an invented kind fails the
client's decode of the whole payload."_ The same rule applies per-method to error
tags, and `crate::rpc` does not observe it.

## Key interfaces

- The refusal path in `crate::rpc` needs to select a tag **per method** rather
  than emit one tag for all of them. The declared union for each method is in
  `packages/contracts/src/rpc.ts`; read it there rather than guessing.
- `ServerMethodNotImplementedError` stays correct for any method whose union
  does include it. This is not a request to delete it.
- The message should still say what was refused and why — the honesty of the
  current refusal is the part that works.

## Acceptance

- [x] `/settings/diagnostics` and `/settings/source-control` render an empty or
      unavailable state. No schema-decoder text appears anywhere on either page.
- [x] Each of the four named methods answers with a tag that its own contract
      error union contains.
- [x] A test enumerates every method this server refuses, reads each one's
      declared union from the contract, and fails if a refusal uses a tag the
      union does not contain. This is the part that stops it recurring — the
      original bug is one method being added without anyone checking its union.
- [x] Methods whose union does contain `ServerMethodNotImplementedError` are
      unchanged. **Vacuous, and worth recording as such:** no union contains it,
      because the tag is not in the contract at all. What is unchanged instead is
      a tag the contract does not name — `no.such.method` — which still answers
      `ServerMethodNotImplementedError` and still names the method.

## Out of scope

- Implementing any of the four methods. See 65 for the diagnostics question.
- Changing what the client draws for an empty state; that is upstream's.

## Comments

### 2026-07-28 — agent. Done

`crate::refusals`: one table pairing each of the seventy methods
`packages/contracts/src/rpc.ts` declares with the tag a refusal of it carries,
and one function that builds the payload. `DispatchError::to_error` now asks it
instead of writing the tag itself. Nothing else about a refusal changed —
same `Exit`/`Failure`/`Fail` envelope, same sentence, same one-request cost.

**The contract left no choice of tag, and that is worth recording.** All four
methods declare a union of exactly one, `EnvironmentAuthorizationError` — and so,
it turns out, does every other method in the file, as its only member or its last
one. So the answer is uniform: a refusal says "authorization" where the truth is
"unimplemented", and the truth is carried in the message, which is the only part
the client renders (`useEnvironmentQuery` squashes the cause and shows
`message`). It is a compromise rather than a fix; the alternative is the tag that
was already on the page. `requiredScope` is required by the class and is
`orchestration:read` — the scope every connected client already holds, so the
refusal does not read as a permission somebody could go and grant.

`ServerMethodNotImplementedError` is **not in the contract at all**, which makes
the fourth acceptance criterion vacuous — no union contains it, so no method was
ever going to keep it. What kept it is the other case: a tag the contract does
not name has no union to decode against, so `no.such.method` still answers
`ServerMethodNotImplementedError` and still carries `method`. The capture
divergence ticket 03 argued for is untouched.

Two tests read the contract back, and the second is the one the ticket asked
for:

- `refusals::the_table_is_the_contract` parses `rpc.ts` — the two `as const`
  method maps, each `Rpc.make`'s `error:` field, and every union member resolved
  through the whole package to its `_tag` literals — and fails on a method the
  contract has grown, one it has dropped, or a pairing its union does not
  contain. The resolver has to be real: unions nest (`TerminalError` is nine
  classes deep in places) and a class's tag is not always its own name
  (`KeybindingsConfigError` is tagged `KeybindingsConfigParseError`).
- `rpc::every_method_this_server_refuses_answers_under_its_own_union` dispatches
  all seventy with an empty payload, keeps the thirty-nine that come back
  `UnknownMethod`, and checks each against its union. It finds the refused set by
  asking rather than by holding a second list.

The third guard is not a test. The table's tag column is a one-variant enum
rather than a string, so a second tag cannot be added without `refusal` failing
to compile — and the fields that tag's own class declares are what the compiler
then asks for. A required field left out fails the client's decode exactly as a
wrong `_tag` does, so this is the same check as the two above, made where it
cannot be skipped.

Then the two pages, driven headless against a release build on `:4774` with
`tools/ui-driver/surface-walk.mjs` — the same tool that found this:

```
--- /settings/diagnostics ---
!! REFUSED: server.getTraceDiagnostics, server.getProcessDiagnostics, server.getProcessResourceHistory
text: … Method not implemented by this server: server.getProcessDiagnostics /
      NAME CPU MEMORY COMMAND PID TYPE KILL / No live descendant processes found. …

--- /settings/source-control ---
!! REFUSED: server.discoverSourceControl
text: … Server environment / Could not scan the server environment /
      Method not implemented by this server: server.discoverSourceControl / Scan
```

No `Expected { readonly "_tag": … }` anywhere in the walk, and the other seven
routes read exactly as they did before. The walk's own refusal detector had to
change with this: it keyed on the `_tag`, and the tag is now whatever the method
declares, so it keys on the sentence — which is the part that did not move.

Also checked from the other side, because a Rust test can prove the tag is in the
union and still be wrong about the fields: the exact payload decoded against
`WsServerGetProcessDiagnosticsRpc.errorSchema` and its three siblings under the
real `effect/Schema`. The old payload fails there with the ticket's own text
(`Expected "EnvironmentAuthorizationError", got "ServerMethodNotImplementedError"`),
and dropping `requiredScope` fails with `Missing key` — so both halves of the
shape are load-bearing. That check was a scratch file and is not committed;
`packages/contracts` is upstream's and stays schema-only.

### 2026-07-28 — agent. Reviewed, and what the review changed

A two-axis review found no missing requirement and no hard standards violation.
Eleven judgement calls; all acted on. Three are worth reading here rather than in
the diff.

**The tag is not inert, and the module doc said it was.** `REFUSAL_SCOPE` claimed
"nothing in the client reads it" — true of `requiredScope`, and not of the
`_tag`. `packages/client-runtime/src/rpc/session.ts:49` maps
`EnvironmentAuthorizationError` from `server.getConfig` or `server.probe` to
`ConnectionBlockedError({reason: "permission"})`: a connection refused on
permission and not retried, which is not an empty state on a page. `server.probe`
is in the refused set, so this is one capability flag away from live — it is
dormant only because this server does not advertise
`capabilities.connectionProbe` (`session.ts:125`), which makes the client probe
with `server.getConfig` instead. The comment is corrected, both rows carry the
warning, and it is the first consequence in the ADR. **Ticket 65, or whichever
implements the diagnostics, should not advertise `connectionProbe` before
`server.probe` answers.**

**`docs/adr/0017` now holds the decision**, which had been living in a `.scratch/`
comment and a module doc: a refusal borrows a tag it does not mean, because the
contract offers no other. Hard to reverse in evidence rather than in code — the
reason it is this tag is a reading of all seventy unions in another language.
ADR-0009 is its sibling and says the same thing one layer in. `CONTEXT.md` gains
**refusal** under `## Protocol`, distinguished from a declined _setting_.

**Set equality against `rpc.ts` is kept, deliberately.** The review's one real
trade-off: `the_table_is_the_contract` asserts the table and the contract name
the same seventy methods, so a purely additive `upstream` merge goes red until
somebody adds a row. Kept, because an unlisted contract method is still refused —
and refused with `ServerMethodNotImplementedError`, which is this ticket's bug
back on the screen. The merge that adds a method is exactly when its union should
be read. The reasoning is in the test's own doc comment and in the ADR, so the
next person to see it go red can disagree with it on the evidence.

The rest: the fuzzy `refused > declared.len() / 2` in
`rpc::every_method_this_server_refuses_answers_under_its_own_union` is now a
named method (`orchestration.replayEvents`, which `tests/socket_handshake.rs`
refuses end to end), because `server/CLAUDE.md` asks a test to assert on the
decision the code made rather than on roughly how much is left to build; the
`_tag`-not-in-union assertion, written verbatim three times, is one
`contract::assert_declares`; the unreachable middle arm of `refusal` and the
`only_one_tag_is_used` test policing it are both gone, replaced by a one-variant
enum that will not compile a second tag without its declared fields; `REFUSALS`
and `declared_error_tag` are private, having no caller outside the module; the
180-line TypeScript parser moved to `src/refusals/contract.rs`, because it
changes when upstream writes the contract differently and the rest of the module
changes when a refusal does; and the prose numbers on the refusal path are
seventy rather than "sixty", with the count of what is _unimplemented_ stated
only where it is a historical claim that stays true.

Also reverted: the edit to `PARITY-LEDGER.md`'s §S2 narrative. Only the status row
changes. The ledger already says "Where the two disagree, the ticket is newer", so
a historical finding does not need to track the code.

### 2026-07-28 — agent. Reviewed again, and two claims that were not true

The review re-ran against the commit. No correctness defect, no missing
requirement, and the set-equality call above survived being argued with. Two
findings were things the first round had _written down_ rather than built, which
is the useful kind:

- The ui-driver README claimed **both** `surface-*` files key on the sentence
  rather than the `_tag`. Only `surface-walk.mjs` had been changed;
  `surface-actions.mjs` still matched `/not implemented|NotImplemented/`. Now it
  matches the sentence, so the README is true. The `NotImplemented` alternative
  was dead in any case — it can now only fire for a method the contract has never
  heard of, and that payload carries the sentence too.
- The comment above claimed the prose numbers agree. `rpc.rs:179` and
  `socket_handshake.rs:103` still said "sixty"; both now say seventy. The claim
  is narrowed to what it actually covers.

**`rpc.rs:3` is knowingly left stale** and is not this ticket's to fix: "roughly
sixty methods. Twenty-four are implemented" precedes a prose enumeration of
exactly twenty-four clauses, and the real figure is thirty-one. Correcting it
means recounting `dispatch` and writing the seven missing clauses — a change
about what this server implements, not about how it refuses.

The count of unimplemented methods is no longer stated anywhere it would drift.
`lib.rs` says "the ones it has no answer for yet"; "thirty-nine" survives only in
the past tense, where it is a claim about what the bug did rather than about what
is left. The alternative — asserting the count — is the fuzzy-count problem this
round removed.

Also: the sentence every refusal carries now has a name and a doc,
`REFUSAL_SENTENCE`, saying that two ui-driver tools match on it and that the
tests spell it out as a literal so a change fails rather than agreeing with
itself. It is the load-bearing discriminator now that the tag is per-method, and
it had been the one part of this with nowhere to live. `refusals::contract` gains
`identifiers` for the comma-list it parsed two ways, and `everything` is
`all_sources`.

Two findings were declined. The refusal payload still drops `method` for a
contract method — the sentence names it, which is all the ticket asked for, and
adding a field would change a payload verified against the real `effect/Schema`.
And ADR-0017 keeps its `## Considered options` heading, which no ADR here has
used before: the ADR format the domain skill documents lists it as an optional
section, so it is sanctioned rather than novel.
