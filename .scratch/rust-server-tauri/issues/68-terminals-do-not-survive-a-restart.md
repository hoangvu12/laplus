# 68 — Terminals do not survive a restart

> _This was generated by AI during triage._

**What to build:** a decision on whether terminal sessions should outlive the
window, given that the current behaviour is deliberate and only half-satisfying.

**Status:** needs-triage

**Found by:** the 2026-07-28 parity audit, ledger R14.

## What happens

laplus reaps every terminal when the window closes. Upstream retains up to 128
inactive sessions with debounced scrollback persistence.

**The current behaviour is declared and reasoned** in `crate::terminal`: restored
scrollback would describe a shell that has already been killed, so showing it
would be a lie about the state of the machine. That reasoning is correct and this
ticket does not dispute it.

What it does not cover is that **upstream's shells are still there.** Upstream
does not restore a picture of a dead shell — it keeps the shell. So the choice
laplus made is between "no scrollback" and "misleading scrollback", when there is
a third option it did not consider: keep the process.

## Why this is triage and not work

Keeping shells alive across a window close is a real commitment:

- **A closed window with live child processes is a surprising thing for a desktop
  application to be.** On Windows especially, a developer who closes laplus
  expects it to be gone. Leaving ConPTY children running is defensible only if it
  is visible and controllable.
- **laplus is a single window with the server inside it** (ADR-0014), not a daemon
  with clients. Upstream's architecture makes surviving sessions natural; this
  one's does not. Retaining shells might mean the server outliving the window,
  which is an architectural change, not a terminal feature.
- **The cost of not having it is modest.** A developer reopens laplus and starts a
  shell. Terminals work well otherwise (tickets 17–18), including a shell
  resolution that **extends** upstream's `ComSpec`/`SHELL` handling.

## The three answers

1. **Keep as is.** The reasoning in `crate::terminal` stands; close this and record
   it so the next parity audit does not re-file it.
2. **Persist scrollback only**, clearly marked as a transcript of a finished
   session rather than a live one. Cheaper than 3, and answers the common case —
   "what did that command print before I closed it".
3. **Keep the shells.** Matches upstream, and is the architectural change above.

Option 2 looks like the best value from here and is deliberately not chosen. Note
it directly contradicts the current declaration, which is _why_ it needs a
decision rather than a patch — someone reasoned their way to the opposite
conclusion and their reasoning should be answered, not overwritten.

## Acceptance

Deliberately not written; it depends on which answer is taken.

What can be said regardless:

- Whatever the terminal shows after a restart, the developer can tell whether the
  shell behind it is alive.
- The declaration in `crate::terminal` matches whatever is decided, rather than
  describing a superseded choice.
