# 31 — Every snapshot is asked for over HTTP first, and refused

**What to build:** two HTTP endpoints the UI already asks for, so that loading a
conversation stops costing a failed round-trip before it starts.

The client loads the shell snapshot and each thread snapshot over HTTP, and
falls back to the socket-embedded snapshot when that fails. This server
implements neither route, so **every** snapshot takes the fallback, and each one
logs a 404 and a warning on the way:

```
error: Failed to load resource: the server responded with a status of 404 (Not Found)
log:   WARN Could not load the environment shell snapshot over HTTP; using the socket snapshot instead.
error: Failed to load resource: the server responded with a status of 404 (Not Found)
log:   WARN Could not load the thread snapshot over HTTP; using the socket snapshot instead.
```

**Status:** done

**Found by:** ticket 03, in `tools/ui-driver/probe-boot.mjs` output while closing
its last two criteria. Invisible in the window — everything renders — and
invisible on the socket, because the failure happens over HTTP.

## The two routes

From the vendored client, which is the only specification either has:

| Route                                       | Loader                                                    |
| ------------------------------------------- | --------------------------------------------------------- |
| `GET /api/orchestration/shell`              | `packages/client-runtime/src/state/shellSnapshotHttp.ts`  |
| `GET /api/orchestration/threads/{threadId}` | `packages/client-runtime/src/state/threadSnapshotHttp.ts` |

Both go through `makeEnvironmentHttpApiClient` with
`buildEnvironmentAuthHeaders`, and the thread loader times out at 6 s
(`DEFAULT_THREAD_SNAPSHOT_TIMEOUT_MS`). The client's own comment gives the
motive:

> The response is gzip-compressible by the transport and keeps the (potentially
> multi-KB) snapshot off the socket.

So this is a **transport optimisation**, not a capability. The socket path
already carries the same data and already works.

## Why it is worth doing anyway

Two things make it more than a warning in a console nobody reads.

**It compounds with the draft poll.** A "New thread" pane subscribes to a thread
that does not exist yet, and the client is given
`retryExpectedFailureAfter: "250 millis"` for that subscription — correct, and
ticket 03 explains it. But each retry re-attempts the HTTP snapshot too, so an
open draft pane produces a sustained ~4/second 404 storm for as long as it is
open. Neither half is a defect on its own; together they are a server answering
four pointless requests a second all day.

**It is noise in the one place a UI bug shows up.** `tools/ui-driver` exists
because the client's console and frame log are the only way to see the UI half of
this application. Ticket 28 was found by reading exactly that output. A console
that is already full of 404s at four a second is a worse instrument, and this is
the repo's only instrument.

## Worth settling before starting

**Whether to implement them or to make the client stop asking.** Not obvious:

1. **Serve both routes.** They return data the server already assembles for the
   socket, so the work is a route, an auth header check and a serialisation —
   not new domain logic. Gets the gzip benefit the client wanted.
2. **Find the flag.** If some capability or config field turns the HTTP fast-path
   off, silencing it costs one field instead of two endpoints. Ticket 03 already
   found that `connectionProbe`'s absence changes client behaviour this way, so a
   switch is plausible — but nobody has looked, and if there isn't one, option 1
   is the answer by default.

Check 2 first; it is a grep, and it decides whether this ticket is small or
medium.

## Not to be confused with

`src/http.rs` currently serves `/api/auth/session` and
`/.well-known/t3/environment` only, both written from the contract with no
capture behind them — ticket 03 calls it the least well-founded code in that
ticket. These two routes are the first _evidence_ of what else the UI wants over
HTTP, which makes them worth capturing properly rather than guessing at: the
reference server is the authority on the response shape, and
`tools/wire-capture/` records only `/ws`.

#### Agent Brief

**Category:** enhancement

**Summary:** Serve the two orchestration snapshot routes the UI already asks for
over HTTP, so the shell and thread snapshots stop costing a failed round-trip
before falling back to the socket.

**Current behavior:** The server answers `GET /api/orchestration/shell` and
`GET /api/orchestration/threads/{threadId}` with a plain 404, because neither is
routed. Every shell and thread snapshot therefore takes the socket fallback, and
each logs a 404 and a client warning on the way. The socket path already carries
the same data and already works, so nothing is functionally broken.

**Desired behavior:** Both routes are served, authenticated the same way the
socket upgrade is, returning the same payloads the socket's opening chunk
carries. A thread that does not exist is a typed `not_found`, not a bare 404. The
socket path is unchanged and remains the fallback.

**Key interfaces:**

- `EnvironmentOrchestrationHttpApi` in `@t3tools/contracts` is the specification
  for both routes — success schemas, `params`, `OptionalBearerHeaders`, the
  `EnvironmentAuthenticatedAuth` middleware, and the error unions. Read it first;
  it is exact.
- `OrchestrationShellSnapshot` is the body of `/api/orchestration/shell`. The
  server already assembles it: it is the inner `snapshot` object of the shell
  subscription's opening chunk (`snapshotSequence`, `projects`, `threads`,
  `updatedAt`), with the `{"kind":"snapshot"}` envelope unwrapped. The builder is
  private to the orchestration module and reusable as-is.
- `OrchestrationThreadDetailSnapshot` is the body of the thread route —
  `snapshotSequence` plus the thread's detail value. This one is built **inline
  inside the thread subscription's description closure**, so it needs lifting
  into something both the socket and the route can call. That extraction is the
  only real refactor in this ticket.
- The `authorize` entry point in the server's auth module already parses
  `Authorization: Bearer …` and `DPoP …` for the socket upgrade. The two routes
  should accept exactly what it accepts; a credential good enough to open the
  socket must be good enough to read a snapshot, or the fallback becomes the only
  working path again.
- `EnvironmentResourceNotFoundError` (`code: "not_found"`,
  `reason: "thread_not_found"`, status 404) is the answer for an unknown thread
  id. `EnvironmentAuthInvalidError` (status 401) is the answer for a missing or
  bad credential.

**Acceptance criteria:**

- [ ] `GET /api/orchestration/shell` returns 200 with a body that decodes as
      `OrchestrationShellSnapshot`.
- [ ] `GET /api/orchestration/threads/{threadId}` for a thread that exists
      returns 200 with a body that decodes as `OrchestrationThreadDetailSnapshot`.
- [ ] A test asserts HTTP and socket agree on both payloads for the same server
      state, in the manner of the existing test that makes the environment
      descriptor agree with the one the socket reports.
- [ ] An unknown `threadId` returns 404 carrying the `not_found` /
      `thread_not_found` body, not an empty 404.
- [ ] A request with a missing or invalid credential returns 401 carrying the
      `auth_invalid` body, and a credential that opens the socket is accepted.
- [ ] `an_unimplemented_http_route_is_a_plain_404` is updated: the shell route is
      no longer among the paths it pins as 404, and its comment naming ticket 04
      as the condition goes with it. The other paths it covers keep their 404s.
- [ ] `the_servers_own_surface_is_never_answered_with_the_ui` still passes
      **unchanged** — these routes must never be answered by the SPA asset
      fallback, and that is more important once they exist than it was before.
- [ ] Booting the real UI under `tools/ui-driver` shows neither the shell
      snapshot 404 nor "Could not load the environment shell snapshot over HTTP"
      in its output.

**Out of scope:**

- The draft-pane 404 storm. It survives this ticket by design — see the
  correction above — and its fix is a client change in an upstream package.
- `/api/orchestration/snapshot` and `/api/orchestration/dispatch`. Both are in
  the contract; neither is called by `packages/client-runtime`. Adding them is
  speculation, and this ticket exists because speculation is what
  `src/http.rs` already suffers from.
- Any edit to `packages/contracts` or `packages/client-runtime`. The contract is
  the specification here, not a thing to change.
- The socket snapshot path, which stays exactly as it is and stays the fallback.
- Recording these routes in `tools/wire-capture/`. The contract is a better
  authority than a capture would be, and `apps/server` is not in the working
  tree to capture from.

### 2026-07-28 — agent. Done

Both routes are served. Triage was right that the shape is not a guess: the
contract gave the paths, the params, the headers, the statuses and the whole
error union, and the payloads were already being built — so the ticket really is
a route, a credential check and one extraction.

The extraction is the only structural change. `Shell::shell_snapshot` and
`Threads::detail_snapshot` are now the single builders for their payloads, and
both subscriptions call them, which is what makes "HTTP and socket agree" a
property rather than a coincidence. The two agreement tests compare whole
payloads, in the manner of `the_descriptor_agrees_with_the_one_the_socket_reports`.

**Three things worth recording, in descending order of how much they cost the
next person.**

#### 1. The AC's 401 could not be implemented as written, and implementing it would have broken the ticket

**`docs/adr/0015` is this in full**, because it is a decision about the shape of
the server's security boundary rather than a note about one ticket, and because
the argument was otherwise spread across four doc-comments. The short version:

Two of the acceptance criteria contradict each other. "A request with a missing
or invalid credential returns 401" against "a credential that opens the socket is
accepted", with the Key Interfaces section saying the routes "should accept
exactly what [`authorize`] accepts". `authorize` accepts an **absent**
credential — permissive is the v1 posture and loopback is the boundary.

That is not a tie to be broken on style. `buildEnvironmentAuthHeaders` in
`packages/client-runtime` returns `{}` when the connection carries no
credential, which is every primary local connection — i.e. every laplus window.
A route that required one would 401 the real client on every request and leave
the socket fallback as the only working path, which is precisely the state this
ticket set out to end. So the routes take exactly what the upgrade takes,
including nothing.

The 401 is still real and still tested: the one refusal `authorize` makes is a
non-local origin, and it reaches these routes as it reaches the upgrade. It
matters _more_ here — a `fetch` from a page elsewhere is a page elsewhere asking
the user's own browser for their project list. One deliberate difference from the
upgrade's 401: no `Access-Control-Allow-Origin: *`. There it lets a browser read
the body instead of a CORS error for a handshake it cannot see into; here the
refused request _is_ the cross-origin one, and the header would be the only thing
the refusal gave away.

#### 2. The correction above needs a correction: the draft-pane _warnings_ do go away

Triage said implementing these routes "converts an _unimplemented-route_ 404
storm into a _correct_ 404 storm of the same volume", warning and all. The volume
is unchanged — that half is right — but the warning is not.
`threadSnapshotHttp.ts` catches `EnvironmentResourceNotFoundError` **by tag**,
with a comment saying a genuinely missing thread is expected, and logs it at
`logDebug` — "Thread snapshot not found over HTTP; deferring to the socket
subscription." Only an error it _cannot_ decode becomes "Could not load the
thread snapshot over HTTP" at warning level.

So a bare 404 is a warning and a typed 404 is a debug line, and that is the whole
reason `http::thread_not_found` exists rather than `StatusCode::NOT_FOUND`. The
console is quieter than this ticket predicted; the network panel is not.

#### 3. The gzip benefit is half-collected, and the reason is a divergence we already declared

`tools/ui-driver` shows the client doing exactly what the ticket wanted:

```
=== CONSOLE ===
(empty — no 404, no "Could not load the environment shell snapshot over HTTP")
=== FRAMES ===
→ orchestration.subscribeShell {"afterSequence":0}
← Chunk {"kind":"snapshot","snapshot":{"projects":[],"snapshotSequence":0,…}}
```

The acceptance criterion is met: the shell 404 and its warning are gone. But look
at what changed on the socket. Holding an HTTP snapshot, the client now
subscribes **with a cursor** — `afterSequence: 0` — asking for a replay instead
of a snapshot. `crate::orchestration`'s declared divergence is that laplus
"honours `afterSequence` by over-answering": it sends the whole snapshot anyway.

So on a real boot the shell now travels **twice** — once compressed over HTTP,
once uncompressed on the socket — where before it travelled once. Nothing is
broken, and on a registry of any size the compressed copy is still the cheap one,
but "keeps the snapshot off the socket" is not yet true and this ticket cannot
make it true on its own. Honouring the cursor is a change to
`Shell::subscribe`, wants a replay log this server does not keep, and belongs to
whichever ticket decides the log is worth keeping. Recording it here because
these two divergences were harmless separately and are not quite harmless
together, and nothing else would have joined them up.
