# 44 — The drift counter cannot see what the CLI already does

> _This was generated by AI during triage._

**What to build:** a decision, then a change, about whether an unrecognised
protocol subtype should be silence.

**Status:** ready-for-agent

**Found by:** the 2026-07-28 parity audit, measured —
`.scratch/rust-server-tauri/2026-07-28-cli-stream-audit/` finding, §"The
measurement".

## What happens

Ticket 15 built drift counters so that when the `claude` CLI moves, this server
notices. Measured against `claude` 2.1.220 with laplus's exact flags, over two
short turns:

```
total lines:                            102
lines that produce nothing at all:       66  (65%)
```

**A third of the stream — 34 lines of 102 — reaches the developer nowhere, and
none of it increments a drift counter.** Not because of a bug, but because
`SystemEvent::Other` and `Delta::Unknown` are silence _by construction_: an
unrecognised subtype matches a catch-all arm that folds to `Nothing` without
counting.

So the counter built to report that the CLI has changed cannot report the ways
the CLI already differs from what this server models. It only sees categories
someone thought of.

Be precise about the 65%: roughly half is redundant rather than lost —
`thinking_delta` and `input_json_delta` re-arrive whole in the buffered
`assistant` message. Those cost liveness, not information. The other half — 25
`thinking_tokens`, 4 hook lines, 3 `status`, 3 `message_delta` usage payloads —
has no second source at all.

## The decision

Should an unrecognised `system` subtype or delta type increment `unknown_events`?

The argument for: that is exactly what the counter exists to report, and it is the
one thing it cannot currently see.

The argument against: the counter would be non-zero on every turn today, against
subtypes this build knows about and chooses not to handle — which makes it noise
rather than signal, and a signal that is always on is off.

**Both are right, which means the answer is probably a distinction rather than a
switch:** subtypes this build has decided not to handle should be _declared_ as
ignored and not counted; subtypes it has never heard of should be counted. That
turns the catch-all from "everything I don't handle" into "everything I don't know
about", which is a different and much smaller set.

Take that as the recommendation, not the specification — if it does not survive
contact with the code, say why on this ticket.

## Key interfaces

- The catch-all arms in `crate::protocol` for system subtypes and for deltas.
- Whatever backs the drift counters from ticket 15, and how they are reported.

## Acceptance

- [ ] A `system` subtype this build has never seen increments a drift counter.
- [ ] A subtype this build knowingly ignores does not, and the list of knowingly
      ignored subtypes is written in one place a reader can find.
- [ ] The counter is zero across a full run of the committed fixtures.
- [ ] A test feeds an invented subtype through the reducer and asserts the counter
      moved. There is no such test today, which is why this was invisible.

## Out of scope

- Rendering any of the four known subtypes — that is 43.
- Live thinking deltas — 53.

## Note on why this was not caught

The committed fixtures in `server/fixtures/claude-cli/` are eighteen recordings of
ticket-shaped scenarios, and **not one contains a hook, a thinking delta, a
`thinking_tokens` line, a `status` line or a `usage` object.** The reducer passed
its golden tests while dropping a third of the stream. Whatever else this ticket
changes, the fixture set should stop being a set of scenarios someone had a ticket
for.
