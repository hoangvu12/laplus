# 37 — The mode the agent reports is no longer visible

**What to build:** not yet decided — a place for the _effective_ model and
permission mode, given that the row which used to carry them has gone.

**Status:** needs-triage

**Blocked by:** 57 — see the triage comment below. The option this ticket calls
best cannot be taken until a runtime log exists.

**Found by:** filed against `1053a3862`, by the change itself, so that what it
gave up is a decision with a record rather than something that quietly went
missing.

## What happens

Nothing, which is the problem. The composer's model picker and runtime-mode
selector show what the agent was **asked** for. The `session.init` row used to
show what the CLI reported as **in force** — after it had resolved a model alias
and applied the developer's own `settings.json` over the mode this server
requested. The two can differ, and now nothing says so.

The data still arrives and is still folded: `SessionState` holds `model` and
`permission_mode` from the `init` line (`crate::protocol`). It is read for
nothing and published nowhere.

## Why the row was removed anyway

It opened every conversation with a sentence upstream has no equivalent of, and
in the ordinary case — no alias, no settings override — it restated two things
already on screen. As the first visibly non-upstream thing in every transcript
it was paying that cost on every conversation to be right on a few. See the
commit, and the **Agent session id** entry in `CONTEXT.md`.

## What to settle before starting

**Whether the divergence is worth showing at all, or only when it exists.** A
row that appears only when the effective mode differs from the requested one
would cost nothing in the common case and say something real in the rare one —
but "nothing here is ever surprising" is a claim this project cannot make on the
developer's behalf, and a row that appears sometimes is one nobody learns to
look for.

**Where it would go if not the work log.** The session already carries
`runtimeMode` on the wire and the composer renders it. A field beside it saying
what the agent actually reported would be the honest shape, but
`OrchestrationSession` is the contract's and adding to it is a divergence in the
one package this fork keeps identical to upstream — `packages/contracts` is the
blueprint, not a place to put things.

**Or whether the answer is a log line.** The developer who needs this is
debugging "why did it ask me / why didn't it ask me", which is a question asked
rarely and answered once. `eprintln!` reaches `logsDirectoryPath`, costs nothing
on screen, and is where the resolved binary path already goes for exactly the
same reason (`crate::provider`, `describe`).

That third option looks best from here and is deliberately not chosen.

## Acceptance

Deliberately not written; it depends on which of the three above is picked.

What can be said regardless:

- A conversation in which the requested and effective mode agree gains no row.
- Whatever is added is reachable by a developer asking "which mode is actually
  in force", without reading the code.
- `packages/contracts` is unchanged.

### 2026-07-28 — triage. The preferred option is blocked, and there is a second reader for the same data

> _This was generated by AI during triage._

**Status stays `needs-triage`**, but the picture has changed in two ways.

**1. The third option — "the answer is a log line" — cannot be taken today.**

This ticket says `eprintln!` reaches `logsDirectoryPath`. It does not. The
2026-07-28 parity audit (ledger R12, now ticket 57) found there is **no runtime
log at all**: no `tracing` or `log` dependency anywhere in the workspace, 63
stderr writes, and the shell captures **only** `startup.log`. A released Windows
build has no console, so **everything written after the window opens goes
nowhere.** `logsDirectoryPath` is advertised to the UI and, past boot, nothing
writes to it.

So the option this ticket calls best is not cheap — it is blocked on 57. That
does not make it wrong; it makes it an ordering fact. **Recorded as
`Blocked by: 57`.** If 57 lands, this becomes genuinely cheap and the third
option is probably the answer.

**2. There is now a second consumer for the same divergence.**

Ticket 52 covers `settingSources` — a query option upstream passes and laplus does
not, which controls **which of the CLI's own settings files it reads**. That is the
mechanism by which a developer's user-scoped `settings.json` silently overrides the
mode this server requested. It is the same divergence this ticket exists to
_display_, seen from the end that could _prevent_ it.

Worth deciding together, because they interact:

- If 52 passes `settingSources` and pins the CLI to laplus's own settings, the
  requested and effective modes would agree in far more cases — and a row that
  appears only on divergence (this ticket's first option) becomes nearly free,
  because it would nearly never appear.
- If they are meant to be allowed to diverge, then displaying it matters more, not
  less.

Neither is chosen here. But "how often can these two differ, and do we want them
to" is a question 52 answers and this ticket assumes, so 52 should probably be
looked at first.

**Unchanged:** the data still arrives and is still folded — `SessionState` holds
`model` and `permission_mode` from the `init` line, read for nothing and published
nowhere. Nothing has decayed; it is still one field away from being usable.
