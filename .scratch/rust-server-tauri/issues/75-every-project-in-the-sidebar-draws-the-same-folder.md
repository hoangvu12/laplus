# 75 — Every project in the sidebar draws the same folder

> _This was generated by AI during a design conversation, 2026-07-29._

**What to build:** `assets.createUrl` for the `project-favicon` resource, and
the route that honours the URL it issues, so a project shows its own icon where
the UI has been drawing a folder.

**Status:** ready-for-agent

**Depends on:** nothing. The client half is already written and shipped.

## Why

`ProjectFavicon.tsx` has asked for a project's icon since the fork. It calls
`assets.createUrl` with `{_tag: "project-favicon", cwd}`, resolves the answer
against the http base, and renders a `FolderIcon` when the answer does not
come — which is every time, because dispatch has no arm for the method and
`crate::refusals` answers it. The folder is not a design choice. It is the
fallback, showing permanently.

Five surfaces render it: the sidebar's project rows, SidebarV2's thread rows,
`ChatHeader`, the command palette, and the project list in Settings. All five
are wrong in the same way and all five are fixed by the same method.

PARITY-LEDGER **M7** is the same missing method seen from the other end —
attachments are accepted and dropped at `orchestration.rs:1009` — and section 7
names the asset URL service as the part with a real cost. This ticket pays that
cost for one of the three resources and leaves M7 the store it also needs.

## The rule this follows

> **The URL is the credential, and it is signed rather than remembered.**

A browser fetching an `<img>` sends no socket credential and has nowhere to put
one, so the URL has to carry its own authority: claims naming a workspace root
and a path inside it, signed with a key only this server holds, expiring in an
hour. A URL that verifies is one this server issued; anything else is a 404.

This is deliberately **not** ticket 73's answer for auth credentials, which are
rows in SQLite. 73 chose rows because a pairing credential must be revocable and
a row is what makes revocation a single `UPDATE`. An asset URL is issued per
project per page load and is never revoked — it expires — so a row per issuance
would be a write and an `fsync` for a favicon. Only the key is stored.

## What to do

1. **Find the icon.** Upstream's order, from
   `reference/t3code-server/src/project/ProjectFaviconResolver.ts`: `t3.json`'s
   `iconPath`, then twenty-one well-known paths, then a `<link rel="icon">`
   scanned out of `index.html`, the two `__root.tsx` locations, the two
   `root.tsx` locations and `public/index.html`. A declared path that does not
   exist falls through rather than failing — the file may not be built yet.
2. **Issue the URL.** `/api/assets/<token>/<basename>`, an hour's life.
3. **Serve it.** Verify, check expiry, and re-resolve the file from the claims.
   The filename in the URL is decoration; upstream's own test passes a wrong one
   and still expects the right file.
4. **Answer the no-icon case with a URL, not an error.** Most projects have no
   icon. The filename is then the literal `project-favicon-missing`, which
   `packages/shared/src/projectFavicon.ts` already recognises — the client draws
   its folder without making a request at all.
5. **Refuse the other two resources by name**, with the sentence
   `tools/ui-driver/surface-walk.mjs` counts, so `attachment` keeps showing up
   as a thing that does nothing until M7 is done.

## Confinement

Twice, and the second time is the one that matters. A path that was a file
inside the project when the token was minted can be a symlink out of it a minute
later, so the check at serve time is about the file actually about to be sent.
The lexical half is the rule `projects.readFile` is already confined by — state
it once and have both read it, rather than folding `..` in two places where only
one of them has `files.rs`'s tests over it.
