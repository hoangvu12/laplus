# 67 — One control request is answered, and the agent is given no tools of ours

> _This was generated by AI during triage._

**What to build:** a decision on two related things — the control requests this
server does not answer, and whether laplus should expose its own tools to the
agent at all.

**Status:** needs-triage

**Found by:** the 2026-07-28 parity audit, ledger R8.

## What happens

**Half one — control requests.** laplus passes `--permission-prompt-tool stdio`
and registers nothing else. So `can_use_tool` is answered (ticket 13, and it
works), and `mcp_message`, `elicitation`, `request_user_dialog` and
`oauth_token_refresh` go unanswered. This is **declared** in `crate::protocol`, so
it is a known choice.

The question the audit could not settle is what the CLI _does_ when a control
request goes unanswered — whether it proceeds, blocks, or times out. That is
observable and nobody has observed it. If any of the four can arrive on an
ordinary turn, an unanswered one is a hang waiting to happen; if they only arrive
for features laplus does not use, the declaration is complete and this half is
`wontfix`.

**Half two — the injected MCP server.** Upstream injects **its own HTTP MCP
server** into every session (`mcpServers: { "t3-code": … }`). That is how the
agent reaches t3code's own tools. laplus injects none.

## Why half two is a real question and not a gap

It reads like a missing port, but it may not be one. Upstream injects that server
so the agent can call _t3code's_ tools. **laplus has no such tools to expose.**
Copying the mechanism without having anything to put in it would be building a
door to an empty room.

So the actual question is: **should the agent be able to call into laplus?** There
are plausible answers — a tool that reads the current diff, or the checkpoint
history, or the work log — and there is a plausible "no": the CLI already reaches
the filesystem and `git` directly, which covers most of it.

This is a product question and it has never been asked. Note that the spec
excludes the **MCP management UI** (13 files upstream) but not this — the CLI
reads its own MCP config and MCP servers already work; injecting one is a
different thing from configuring them.

## The decision to take

Split it:

1. **Control requests** — settle empirically first. One capture per request type,
   or a reading of the CLI's behaviour on an unanswered control request. Then
   either implement the ones that can occur, or complete the declaration with
   evidence. This half is small and should not wait for half two.
2. **Injected MCP server** — a product question. If the answer is "no tools", say
   so and close it; the declaration in `crate::protocol` then covers everything.

## Acceptance

Deliberately not written; it depends on both answers.

What can be said regardless:

- No control request the CLI can send on an ordinary turn causes a hang.
- Whatever is decided about injected tools is written down where the next parity
  audit will find it, so it is not re-filed as a gap.
