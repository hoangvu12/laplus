# 69 — A retried command is refused as already existing

> _This was generated by AI during triage._

**What to build:** a decision on command idempotency — currently safe, not
idempotent, and visible to any client that retries.

**Status:** needs-triage

**Found by:** the 2026-07-28 parity audit, ledger R15.

## What happens

`commandId` is accepted and not remembered. **Declared** in
`crate::orchestration`, so this is a known choice.

Upstream keeps an `OrchestrationCommandReceipts` table, so a re-dispatched command
answers with the sequence the first one committed at — the retry is a no-op that
returns the original result. laplus refuses the second dispatch as "already
exists".

The current behaviour is **safe** — nothing is applied twice — and that is the
property that matters most. What it is not is idempotent, and the difference
reaches the client: a retry produces an error rather than the original answer, and
the client cannot distinguish "your command was already applied" from "your
command failed".

## Why it is triage

**It is a symptom of ADR-0016, not an independent gap.** Upstream is
event-sourced — `OrchestrationEventStore`, `decider.ts`, `projector.ts`, a
projection pipeline and 34 projection migrations. laplus keeps current state only,
deliberately. Command receipts are natural when every command already commits at a
sequence; they are a new table with new lifetime questions when nothing else is
sequenced.

So the question is not "should we add receipts" but **"how much of the retry
story does a client actually need, given that this server is not event-sourced?"**
Three levels:

1. **Nothing.** Keep the declaration; document that clients should not retry
   commands, and make the refusal say so clearly rather than "already exists".
   Cheapest, and honest.
2. **Remember the outcome, not the sequence.** A bounded map of recent command ids
   to their result, so a retry within some window returns the original answer.
   Gets most of the value without a sequenced store. Needs an eviction policy and
   a decision about whether it survives a restart.
3. **Full receipts.** Matches upstream, and pulls in the sequencing that ADR-0016
   declined.

Level 2 looks like the right value from here and is deliberately not chosen.

## Is anything actually broken

Not that has been observed. This was found by reading the two servers against each
other, not by seeing a retry fail. **Before doing any of the three, find out
whether the client retries commands at all** — if `packages/client-runtime` never
re-dispatches a `commandId`, level 1 is obviously right and this closes cheaply.
That check is worth doing first and is most of the triage.

## Acceptance

Deliberately not written; it depends on the level chosen.

What can be said regardless:

- A command is never applied twice.
- If a client does retry, what it gets back is comprehensible — it can tell
  "already done" from "failed".
- The declaration in `crate::orchestration` matches whatever is decided.
