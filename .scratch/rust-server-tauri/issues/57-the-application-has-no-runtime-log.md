# 57 — The application has no runtime log

> _This was generated by AI during triage._

**What to build:** a log that exists after boot, in the directory this server
already tells the UI about.

**Status:** ready-for-agent

**Found by:** the 2026-07-28 parity audit, ledger R12.

## What happens

There is no `tracing` or `log` dependency anywhere in the workspace. Diagnostics
are 63 `eprintln!`-family writes to stderr.

The shell captures **only** `startup.log`. A released Windows build has no
console. **So everything written after the window opens goes nowhere.**

Meanwhile `logsDirectoryPath` is advertised to the UI as though it holds
something, and `localTracingEnabled`, `otlpTracesEnabled` and `otlpMetricsEnabled`
are hard `false` in `crate::config` while their URL settings are read and stored.

The consequence: **when a developer reports a bug, there is nothing to ask them
for.**

## Why this is worth doing before more features

Every other open ticket gets harder to diagnose without it. It is also a
prerequisite in one specific case: **ticket 37's preferred option is a log line**,
and it cannot be taken while the log does not survive boot.

## Key interfaces

- A logging facade — `tracing` is the obvious choice and its ecosystem gives file
  rotation for free, but the choice is open. What matters is that the 63 existing
  stderr writes migrate rather than being joined by a second mechanism.
- The shell's existing `startup.log` capture should become the boot end of one
  log, not a separate file that stops when the window opens.
- `logsDirectoryPath` must point at something real.
- The three hardcoded `false` tracing flags: either wire them to the URL settings
  that are already read, or make the settings honestly unavailable the way 45 does
  for providers. Pick one; leaving a setting that is stored and ignored is the bug
  pattern this ticket exists to end.

## What to be careful about

**This is a public repository and logs get pasted into issues.** Prompts,
file contents and paths flow through this server. Decide what a log line may
contain before writing 63 of them — the existing `.gitignore` rule for
`.scratch/wire-capture/raw/` exists because unredacted captures carry live session
tokens, and the same care applies here.

## Acceptance

- [ ] A file in `logsDirectoryPath` receives entries produced after the window
      opens, in a released build with no console.
- [ ] `startup.log`'s content appears in it, or it is clear where boot logging
      ended and runtime logging began.
- [ ] The log rotates or is bounded — an application that runs for days does not
      fill a disk.
- [ ] The existing stderr writes go through the new facade; `eprintln!` is not
      left as a second path.
- [ ] Levels work: a developer can get more detail without a rebuild.
- [ ] The three tracing settings are either functional or honestly unavailable.
- [ ] What a log line may contain is written down.

## Out of scope

- OTLP export itself, unless wiring the existing settings turns out to be trivial.
- The diagnostics settings page — 65.
