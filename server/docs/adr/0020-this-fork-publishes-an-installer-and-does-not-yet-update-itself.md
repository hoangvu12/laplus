# ADR-0020 — This fork publishes an installer, and does not yet update itself

Date: 2026-07-29
Status: Accepted

## Context

Two absences arrived together and have been treated as one question for long
enough to file two tickets about it. Ticket 66: `server.updateServer` and
`server.updateProvider` are unimplemented, `capabilities.serverSelfUpdate` is
false, and `tauri.conf.json` configures no updater — so somebody who installs
laplus has no route to a newer one except finding an installer. Ticket 70: what,
if anything, this fork publishes at all.

The tickets could not be decided separately, because **self-update needs
somewhere to update from**. That is a release feed, a key, and a standing
commitment to keep publishing to it — a larger claim than a plugin.

### What was actually true, checked rather than assumed

Ticket 70 was written against a repository state that no longer exists. It
records nine upstream workflows firing, `release.yml` on a three-hourly schedule
"attempting to cut releases from a fork". The GitHub API says otherwise:
`hoangvu12/laplus` has **two** workflows, `CI` and `Rust`, both this project's
own; **zero** releases; **zero** tags. The re-founding commit `2c9487a` left
upstream's `.github/` behind, and no commit in this history has ever contained
`release.yml`. Nothing has been publishing, and nothing was at risk of it.

So the question was never "how do we stop upstream's release job" but the
plainer one underneath: does this fork ship anything to anybody?

### What upstream does, and how much of it transfers

`pingdotgg/t3code`'s `release.yml` is 40 KB and the useful part is small.
Tags `v*.*.*` plus a three-hourly nightly cron; a five-artifact matrix through
electron-builder; **GitHub Releases as both the download page and the auto-update
feed** — electron-updater reads the `.yml` manifests published beside the
binaries, with `.blockmap` files for differential downloads; Azure Trusted
Signing for Windows; an npm CLI publish, a Vercel deploy of the hosted app, and
a Discord announcement.

The matrix, the CLI, the hosted deploy and the relay configuration are about a
product with a hosted half and a team behind it. What transfers is that **the
feed is just GitHub Releases**, which is the fact that makes ticket 66's
"infrastructure this project does not currently have" much smaller than it
sounds. Tauri's updater reads a static JSON manifest and a release asset serves
one perfectly well.

### The two signatures, which are not the same thing

Worth writing down because they are routinely conflated, and the conflation is
what makes self-update look more expensive than it is.

- **Authenticode**, which is what stops Windows SmartScreen calling the
  publisher unknown. Upstream buys this through Azure Trusted Signing. It costs
  money and an identity check.
- **The updater's own signature** — minisign, generated by `tauri signer
generate`, free. It proves an update payload came from whoever holds the key.
  It does nothing for SmartScreen.

An updater needs the second. Only a paid certificate gets the first, and a
laplus installer built by hand already warns today, so shipping unsigned changes
nothing about the experience — it just makes it visible to more than one person.

## Decision

**This fork publishes a Windows installer, on a tag, and nothing else.**
`.github/workflows/release.yml` runs `cargo xtask release --measure-install` on
a Windows runner when a `v*.*.*` tag is pushed and attaches the NSIS installer
and `docs/artifact-size.md` to a GitHub Release. A `workflow_dispatch` runs the
same build and publishes nothing, so the pipeline can be exercised without
cutting a release.

Three things that fall out of it, recorded because they are decisions rather
than details:

- **No nightly cron.** Upstream's exists to feed a nightly channel with users on
  it. A scheduled publish here would be noise with a version number attached.
- **`tauri.conf.json` is the version, and the tag is checked against it** rather
  than written into it. Upstream aligns package versions to whatever the release
  names; here the file is the decision, because it is the number the installer
  and the executable's version resource carry. A CI rewrite would leave the tree
  and the published artifact permanently disagreeing. Note that this is _not_
  the version the window reports — ADR-0011 makes that the UI bundle's, on
  purpose, and the two numbers differ without either being wrong.
- **The Rust suite runs in the release job.** A tag can point at any commit, and
  neither existing workflow fires on one. The TypeScript suite stays out: its
  known-red 15-second timeout would gate every release on a flake, which is the
  same as having no gate, and `ci.yml` covers that half on `main`.

**Self-update is deferred, not refused.** `capabilities.serverSelfUpdate` stays
false and states the truth. The updater is a follow-up, unblocked the moment a
release exists to update from, and its remaining cost is a signing key the
maintainer holds — not infrastructure.

**Provider version advisory (`server.updateProvider`) is untouched by this** and
remains available to take alone: it checks a source that already exists and
commits this project to publishing nothing.

## Consequences

- **Ticket 70 is closed as overtaken.** Its premise is false and its acceptance
  item — "it is known, not assumed, whether `release.yml` can publish anything
  from this fork" — is answered: there is no `release.yml` but this one, and it
  publishes exactly what this ADR says.

- **The first tag is a commitment.** Publishing an installer means somebody may
  install it, and the honest handling of a bad release from here is another
  release rather than a quiet deletion.

- **SmartScreen will warn**, and that is now visible to whoever downloads rather
  than only to the developer who built it. Buying a certificate is a separate
  decision this does not take.

- **Half of ticket 24's clean-machine criterion becomes routine.** A runner is a
  Windows that has never seen laplus, and `--measure-install` proves the
  installer runs there and shows what it wrote. It does not prove the
  application launches, and these images already carry the WebView2 runtime, so
  the absent-runtime criterion stays untested and unticked. Neither is claimed.

- **The release job is the only place `cargo tauri` is installed in CI**, and it
  compiles the CLI on a cold cache. That is minutes on the first release of each
  cache generation and near-nothing afterwards.

- **A release leaves `docs/artifact-size.md` rewritten in the runner's tree**,
  which is published as an asset and never committed. The committed copy is
  whatever the last local `cargo xtask release` wrote, and can therefore lag.
  Worth knowing before reading it as current.
